# Zero agent guidance

## Start with the task

Read `PRODUCT.md` for product and safety boundaries and `docs/context/START-HERE.md` for current work pointers. Treat historical directions as scoped to their original work, not authority for a new run. Consult `AGENT.md` for repo layout and commands, and the relevant handoff, research or `docs/solutions/` only when useful. Check a command or tool before claiming it is unavailable.

Follow the owner’s current request and preserve existing changes. Coordinate ownership before editing files shared with another session. Use isolated worktrees for concurrent writers when needed. Do not reset, stash, overwrite, delete or interrupt another session’s work.

Ordinary questions do not require ledger entries, research files, or handoff updates. Record the decision, evidence, next check and holds when a genuine handoff needs them or the owner requests a durable record. Keep historical asks and evidence accessible without treating them as new approval.

## Safety and resource limits

`PRODUCT.md` governs guest writes, Labtest, property ownership, privacy, penalty dialogs, flags and pilot deployment. Never test against pilot RDS, expose secrets, bypass git or test hooks, or authorize a real-guest write or send by inference. Verify the target and obtain the required authorization before schema pushes, destructive database operations or deleting volumes. Use the product’s approved deploy path (main via `ops-deploy.sh` bundle sync, see `PRODUCT.md`) and verify the current property and authority before live work. Production and authorization approvals must come from the owner in the executing session, not via another agent; the Labtest exception remains as specified in `PRODUCT.md`.

This VPS has previously frozen under heavy checks. Run `tsc`, `tsgo` and affected-app typechecks via `bash /home/orca/bin/remote-typecheck.sh <clean worktree> --app <mail|server-pilot>` on the final release head. Prefer one integrated release check covering remote typechecks for affected apps and focused workflow tests rather than duplicating full checks per PR. Reuse passing evidence only when the relevant source, dependencies and build configuration are unchanged and the evidence still applies to the release head; any changed source, dependency or relevant build configuration requires the affected checks on the new head. Targeted Vitest and `node --test` may run locally: coordinate at most three concurrent local test runs across harnesses, check active tests and resource use before starting, and leave at least 20% CPU and available RAM headroom. Limit test workers as needed; if headroom or the shared cap cannot be maintained, narrow the run or use the approved remote route. Before tests, unset `DATABASE_URL`, `VITEST_ALLOW_PILOT_RDS`, and `TEST_DATABASE_URL`. DB-backed suites may be skipped (owner 2026-11-02); report them as skipped, never passed. After a passing remote typecheck for the same SHA and app, `SKIP_TYPECHECK=1` avoids the redundant pre-typecheck in `remote-vitest.sh`; the Vitest run still takes the EC2 lock. Record affected-app results separately. Read-only git in assigned worktrees is allowed. Never bypass a denial. Stop processes you start by PID.

HMS read-only lookups and unsaved prepare previews may run in parallel in separate verified browser sessions without a policy-level property lock. Existing routes may still enforce one; do not bypass their checks. Serialize live writes or amends affecting the same confirmation or Labtest guest, keep duplicate/preimage checks and Save in the same protected operation, and revalidate after asynchronous preparation. Narrow an existing broader lock only with evidence that its write-safety and session guarantees remain intact.

For flag changes, verify the durable environment source and effective environment of every affected PM2 process (`http`, `worker`, `ai-worker`, `remote-http`) before enqueuing work. Confirm property-specific readiness and a live canary on the final SHA before declaring a workflow on.

GitHub Actions are reserved for the authorized Outlook installer workflows. Do not add, enable or trigger other workflows. Never run repo-wide lint or formatting; use targeted checks when necessary.

## Changes and verification

Keep changes focused and reviewable. Prefer small, bite-sized PRs; roughly 500 changed product lines is useful guidance, not a hard cap. For workflow work, keep a behavior in a connected end-to-end workflow slice (UI → route → tool); do not split it into dormant-helper-only PRs. Shared source, safety and deployment fixes may be independent slices. Merge current main into a long-lived branch before its first review.

Launch Greptile Apex on every PR's final code head and prefer one combined independent/Apex review for that head; do not review only intermediate WIP commits. The automated merge gate does not require a successful Greptile check or completed review, including when the check is failed, unavailable or unfinished; it must verify the exact PR head and block known unresolved P0/P1 review threads. Before release, every included PR diff needs a completed independent review: use completed Apex review when available, or another reviewer if Apex fails, is unavailable or remains unfinished—do not wait indefinitely for a successful Greptile check. Triage any actual Apex findings available for the release before deploying it; fix valid P0/P1 findings and record a disposition for findings judged invalid. Repeat affected checks and review when source, dependencies or relevant build configuration change. Prefer one integrated release validation covering affected-app remote typechecks and focused workflow tests, and reuse unchanged evidence only when it still applies to the release head. The coordinator reads each product diff. Merge through `scripts/orch/merge-gate.sh`. Run independent checks in parallel when safe; honor explicit test-first requests without mandating red-first or forbidding them. Never use `--no-verify`.

If deleting an entity literal triggers a stale-baseline failure, run `node scripts/check-entity-literals.mjs --print-baseline` from `apps/server-pilot` into a temporary file; replace `scripts/entity-literals-baseline.json` only after the command succeeds, then review and stage the baseline diff. Never redirect output directly to the baseline: the script reads it as input.

## Evaluation and evidence

Use production-equivalent input for replay, independent truth data for accuracy, and report the source, sample size and uncertainty. Apply owner-confirmed workflow bars within their scope. Identify proposed bars as proposals, not owner-approved targets. See `PRODUCT.md` and its linked details. Small exploratory samples do not establish a production pass. Compare the same versioned rows and measure baseline noise when it matters. Prove any live tool path with an appropriate read-only probe before batching.

Choose model and agent routing based on the actual task, risk, cost and current owner direction. Historical run-specific model assignments and orchestration recipes are not universal defaults. Avoid extra agents, reviews and documents that add no useful evidence.
