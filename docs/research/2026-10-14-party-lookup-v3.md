# Party lookup v3 — design spike (2026-10-14)

**Verdict: rebuild the evidence path, not the strict bind gate.** Current design knows names from one email and searches a bounded simulated HMS list. Staff also use imported/past reservation records, party kind, agency identifiers, vouchers, and thread context. The conservative offline map adds 7/95 expected-party retrievals but no auto-binds; the cohort is in-sample and only 3/95 rows are quotes, so this is not ship evidence.

Scope: design + offline script only. No runtime lookup change, HMS call, production-data write, or typecheck.

## 2. Failure taxonomy

R7's aggregate gives 9/95 truth rows never retrieved, 86/95 retrieved, 55/95 bound by the production picker, and a 72/95 perfect-picker ceiling. The offline replay reproduces the 9 retrieval misses. A case-level replay of the 14-case `86 − 72` gap shows the expected HMS row is in picker rows in every case, but the strict `applyPartyBindRule` rejects the perfect pick because no strong same-kind extracted candidate claims all distinctive words in the expected row. This is a token-claim gate failure in the simulated answer-key replay, not a strength or uniqueness failure. The R7 report still has no case-level live-picker picks/reasons, so the separate `72 − 55` picker gap remains unclassified; do not assign it to aliases/person/domain causes without its request/response trace. ## 3. V3 design

**Keep every existing HMS choice visible. Use signals to rank and explain, not hide options.**

1. **Evidence ledger per hotel.** Collect typed evidence, not a global alias list: `{hotel, senderDomain, partyKind, HMS nativeId, HMS displayName, source, supportCount, disagreementCount, lastSeen, staffConfirmed}`. Sources: staff-confirmed picker choice; prior successful reservation with same sender/thread; agency/company fields from confirmations/vouchers; exact signature/body mention; explicit IATA/external account ID. Keep guest, agency, company and AR account as separate kinds.
2. **Domain mapping is a learned prior, not an email fact.** Learn from independent historical confirmations/reservations. Require at least two distinct prior reservations, same party kind/native ID, no conflicting labels, and hotel scope. On a new domain, show a “likely party” suggestion; staff confirms once. Save only after an explicit pick; record evidence and allow correction. Domain mismatch, shared/public mailbox, one-off evidence, or conflict means no auto-bind.
3. **Bounded search loop.** Seed searches from extracted agency/client, signature/body mentions, staff-confirmed domain map, IATA/account identifiers, and linked thread/history. Query one HMS kind at a time. After each result, the model may propose a novel refinement term from visible mail/HMS evidence; cap at 3 refinement rounds and the existing row cap. Stop on duplicate query, unchanged result set, refusal, truncation, or time budget. Each suggestion cites the source signal and the exact HMS row; never invent an ID. Log query → returned rows → evidence → final pick for replay.
4. **Strict bind authorization stays.** Preserve the current same-kind strong claim (exact normalized name or all distinctive-name tokens), high-confidence pick, unique strongest HMS row, no competing claim, and untruncated results. A new/unconfirmed domain is never enough. A staff-confirmed map may count as corroborating evidence only after the map policy is approved and independently validated. Any competing agency/client claim or conflict returns to staff.
5. **Staff UI.** Show the current inferred party, evidence chips (“email domain,” “signature,” “prior HMS reservation,” “voucher/IATA”), searched terms, all HMS candidates by kind, and why the system abstained. Keep manual Find in HMS available. After staff selects a row for an unmapped domain, offer a hotel-scoped “remember for future emails from this domain” confirmation. Never silently save or remove choices.
6. **Real answer key before production.** Cheapest reliable path: add a proposed quote-finalized/party-confirmed event (no such event currently exists in source) to log staff-confirmed party choices with message/thread ID, hotel, HMS kind/native ID, and evidence snapshot; redact mail body and avoid storing guest names. Where policy permits, join historical reservations to sender domain and confirmed HMS party. Use chronological holdout by reservation, not the same domain labels used to select test emails. Include verified private/individual cases, shared-domain conflicts, and wrong-bind negatives.

## 4. Offline domain-map prototype

Added [`party-domain-map-prototype.ts`](../../apps/server-pilot/scripts/party-domain-map-prototype.ts). This retrieval-only ablation adds a **weak** `sender_domain_label` candidate for domains with at least two found answer-key rows and unanimous agency labels, then uses the existing simulated search, picker, and unchanged strict `applyPartyBindRule`. It does not promote the domain signal to strong or validate the v3 history policy: the test rows do not prove distinct prior reservations, native-ID agreement, or hotel scope. All 95 expected labels in this cohort are agencies, so company binds are not evaluated. The prototype prints aggregate metrics and generic gate reasons only; no names/domains, mail, IDs, or per-case rows.

| Change                                   |          0/95 |    unchanged |                                     +7/95 |              unchanged |

Map qualification yielded 19 domain entries covering 65/95 emails. Keeping the added candidate weak raises expected-party retrieval and picker-row coverage from 86 to 93/95, but adds 0 auto-binds and 0 perfect-picker ceiling. The 100% precision values are unchanged baseline binds on the same answer-key cohort, not domain-map validation. R2 has 0 verified private-party negatives. Candidate universe is simulated, not HMS; row order, duplicates, live matching, and real IDs can differ. The R7 55/95 result is a different picker scenario and cohort mix; this replay shows retrieval-only in-sample lift, not production quote-path performance.
