## Proposed adapter

1. Use Pomerado only for isolated authoring/review. If using a write mint, use the project-allowed Labtest context: the mint itself performs one live write. Do not expose its standalone MCP as the staff runtime.
2. After native DOM, item codes, and property policy are proven, adapt the deterministic operation into a Zero-owned `previewAddOns({property, stay, rows})` / `commitAddOns({same, previewDigest, grant})` path on Nava’s existing slot. `rows` stays undefined until the native contract is evidenced; use a dedicated Add-On gate and Zero-owned property/stay-bound authorization. Product hard rules allow writes only on Labtest. [PRODUCT.md:49](</home/orca/orca/workspaces/zero/plan-pomerado-1026/PRODUCT.md:49>)
3. Return per-row outcomes; after any possible or partial commit, read back and reconcile each row before retry. Do not treat the existing stay digest as an Add-On idempotency key. Keep shuttle separate.
