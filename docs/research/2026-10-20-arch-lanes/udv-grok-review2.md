**No migration?** False. `mail_ingest_source_receipt_identity_uidx` (`mail.ts:719`) is one row per `(ingestMailboxId, pop3Uidl)`. A `#t:` suffix on the extra copies avoids that index only by storing a different UIDL, and the pre-route duplicate check (`store.ts:280-298`, `:1642-1658`) then treats the first receipt as the whole mail. The receipt unique key has to include `transportId`, or the second copy never gets a receipt and the next poll skips it. That is a migration.

**Primary byte-identical?** Only if the primary is inserted alone, with today's `meta.messageId` and raw `meta.pop3Uidl`, and extra copies cannot roll that transaction back. `findCanonicalCandidate` on another transport can write this poll's raw UIDL onto an existing row (`store.ts:688-689`) before the primary insert (`:782-790`). One unique violation aborts `db.transaction` at `:433`. Same id as today also requires the caller to keep `candidateMessageIdForPop3Uidl(mailbox, rawUidl)` (`worker.ts:338`). `parseAndPersist` does not (`store.ts:2280`).

**Centurion live ingest?** A unique Centurion `To` with no other active transport in `To` stays one row: direct-To returns `unique` (`store.ts:389-390`) and the design's unstamped extra set is Cc/Bcc/From. A corroborated stamp does not win when `To` names two or more active transports: `multi` quarantines at `:343-354` before the stamp at `:356-386`. `findDirectToTransport` is all active transports (`:1859-1873`), not the hotel allowlist. After UDV-1 adds davinci/epick/kmgidi, those Centurion `To`+DV `To` mails quarantine. Research counts 11 such mails in 30 d. Centurion HMS is already refused when From/To/Cc contains a DV identity (`mailbox-hms-origin-bind.ts:101-117`); fan-out does not change that.

**Outlook pane?** `staffQuoteSource` filters `transportId = activeTransportId` and `messageIdHeader`, `limit(2)`, and throws `PRECONDITION_FAILED` when `matches.length > 1` (`workstation.ts:777-791`). `message_transport_header_idx` is not unique (`mail.ts:372-374`). One new row per mailbox is one match. A second POP copy that does not reconcile on that transport (`findCanonicalCandidate`, `canonical-identity.ts:101-134`, same direction, same From/To/Cc, timestamps within 120 s) inserts another row with the same header. The pane then fails for that mailbox. Bcc is not in the HMS origin scan (`mailbox-hms-origin-bind.ts:101-106`); it is not in this lookup either.

**N copies in one call?** `lockCanonicalMailbox` is one `pg_advisory_xact_lock` per transport (`canonical-identity.ts:62-65`). N transports means N locks inside `store.ts:433`. Take them in sorted id order or two polls can deadlock. The receipt insert does not conflict across transports until the unique key includes `transportId`. `mail_thread_transport_root_uidx` is `(transportId, threadRootId)` (`mail.ts:320`); `resolveThreadId` uses the raw UIDL only in the no-Message-ID root (`store.ts:2179`), so two copies on one transport with no Message-ID collide. `mail_live_admission_canonical_uq` is `(transportId, canonicalMessageId)` (`mail.ts:696`) and is safe if each copy has its own message id. `promoteQuarantineId` deletes one quarantine row (`store.ts:945-948`); a second delete in the same transaction is a no-op, but a failure after the first copy rolls the delete back with the insert.
