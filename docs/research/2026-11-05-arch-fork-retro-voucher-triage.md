## 2. What the shipped W13 data path does—and does not—authorize

At final deployed SHA `20e17dd…`:

1. **Admit only current inputs.** `buildInboundPrompt` records attachment text only to the extent it was included under the prompt budget, including attachment identity and a deterministic digest of the actual masked text (`extract.ts` around lines 196–252). The visual path admits bounded PNG/JPEG and at most the first three rendered PDF pages, records page/source identity and digests, and tracks skipped/unread inputs (`extract.ts` around lines 393–553). A model-generated digest is not authority.
2. **Require traceable proposals.** `workflowProposalSchema` carries a role, exact excerpt, and optional source pointer. `sanitizeWorkflowProposal` matches message excerpts to the selected body/subject or attachment excerpts to exactly one admitted current source; it replaces source digests with server-computed values, rejects missing/foreign pointers and unsafe values, and marks visual proposals `reviewRequired:true` ([final schema](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/extraction/schema.ts#L34), [sanitizer](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/extraction/schema.ts#L473), [source handoff](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/extraction/extract.ts#L706)). Visual “review required” is an uncertainty cue, not proof that the OCR/vision value is correct or that a staffer reviewed it.
3. **Project to editable Create fields, not native IDs.** The server builds field metadata with origin/evidence; when the staff state owns a path, `Object.hasOwn` makes that value authoritative even if it is `false`, `null`, or an empty array. Otherwise an accepted proposal is only a suggested field value ([`work-item-effective.ts`](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/work-item-effective.ts#L92)). `field.accept`/`field.edit` persist user-owned state/events ([`work-items.ts`](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/work-items.ts#L2463)). Distinct guest lists suppress ambiguous shared guest-name proposals; native guest/agency/company IDs are not inferred from labels.
4. **Make HMS Prepare the boundary.** Pane Create input requires numeric native party selections where needed ([`pane-create-cloud-input.ts`](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/pane-create-cloud-input.ts#L105)). Prepare is source/cursor-bound, requires explicit native guest selection, checks the current HMS price and normalized request, then issues a one-use grant only after rechecking the source ([`pane-cloud-preview.ts`](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/pane-cloud-preview.ts#L532)). Commit consumes that bound grant separately. Thus “source grounded” means a field can be reviewed and edited; it does not mean source data has selected an HMS profile, rate availability or final price.

The UI surfaces a review-attachment cue for visual values in the Create card, but I found no evidence of a complete mounted-pane staff walkthrough on this SHA. Backend extraction/projection/Prepare and native readback are useful proofs, not pane acceptance.

## 4. W14 result: frontdoor and multiple independent asks

### Plan versus actual model

W14’s plan said distinguish a human travel-agent request from a system notice generically; a self-sent pre-stay confirmation must describe an existing booking and never become Create; a separate current ask should remain a staff handoff; completing one action must not clear another; and a remaining filing task must keep the mail pending. See [W14 estimate](/home/ubuntu/projects/zero/docs/plans/2026-11-05-001-feat-centurion-core-completion-plan.md:190) and [W14 acceptance](/home/ubuntu/projects/zero/docs/plans/2026-11-05-001-feat-centurion-core-completion-plan.md:206).

Final implementation has three bounded pieces:

- `existing-stay-information.ts` requires sender == selected mailbox, a pre-stay/pre-arrival subject and a confirmation number from subject or extraction; `currentAuthoredMessageText` removes quoted/forwarded history; `groundedSeparateAsk` accepts only an exact <=200-character authored excerpt ([source](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/existing-stay-information.ts#L5)). `work-items.ts` refuses to project a Create draft for that existing-stay mail; if the separate authored ask is an allowed actionable type, it is shown as staff work instead ([source](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/work-items.ts#L2025)). Safe, but narrower than all senders/all asks.
- `triage.ts` exempts a current authored agent request from routine-system-mail handling only when the current-message request regex matches and the haystack identifies **TBO or Travelit**. The other system-notice paths are known vendor/domain patterns ([source](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/triage.ts#L612)). So “generic travel agent” is not established: other providers may be handled by the model, but no broad sender/corpus evaluation here demonstrates it.
- `reservationist-task-completion.ts` keeps distinct, source-spanned tasks/acknowledgements across reads where the location/kind is unique; ambiguous tasks stay run-scoped ([source](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/reservationist-task-completion.ts#L19)). `voucher-pending.ts` keys a voucher review to message revision plus exact file ID/hash/identity and clears it only by matching native filing or selected-file acknowledgement ([source](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/voucher-pending.ts#L21)). `work-items.ts` includes unhandled voucher/task history in the “outstanding” guard so a later hotel reply cannot auto-complete that item ([source](https://github.com/kufupa/Zero/blob/20e17dd0137e8791e76c06bd5fb16fdbd9cfbd20/apps/server-pilot/src/ai/work-items.ts#L1638)). This protects the demonstrated voucher-Filing task, not a universal proof that every combination of independent requests stays open.

## 6. Cost, ROI and failure prevention

**No numeric ROI is supportable.** There is no comparable monetary value for reduced staff work or avoided wrong bookings, no invoice/token bill by feature, and no attributable counterfactual. The usage proxy shows recorded response volume/cost per lane window; large cached prompts dominate totals, so response count is not labor. Do not sum the table across lanes or call those values Azure spend. Good return is evidenced qualitatively by (1) a candidate-only attachment validator defect being fixed before deployed Create; (2) a source-bound, editable text-PDF path completing one fake Labtest booking with native readback; (3) avoiding native party-ID invention; (4) observed wrong/omitted fields being exposed and several risky CMS polarity/source cases corrected; and (5) preserving an independent named PDF task after booking/reply. Bad/unmet return: the same run still exposed model omissions and visual misreads, coverage stayed narrow, and no actual staff-pane walkthrough/corpus acceptance was performed.

Concrete next-time safeguards:

1. **Pin preconditions at dispatch.** Before implementing a claimed sanitizer bug, list the fetched base SHA and show whether the schema/property exists there. Keep a candidate-only defect table with candidate SHA, failure locus and first merged fix. This prevents retroactively attributing an unmerged-branch defect to deployed main.
2. **Test extraction and sanitizer separately without new framework.** For the approved existing checks, retain one recorded raw-model result and compare it to sanitized output; say “model omitted” versus “sanitizer dropped” only when the raw result proves which. Treat `false`/negative choices as first-class facts and include same-stay/quoted-history polarity counterexamples.
3. **Gate source pointers on actual admission.** Assert current message/subject, exact admitted text, exact rendered page, pointer identity/page, digest, and the stored field’s source metadata. Keep text excerpts distinct from vision values. Never validate by concatenating history or trusting a model hash.
4. **Use a compact format matrix tied to outcome.** One readable text PDF, a scan, PNG and JPEG should each report: prompt/admission status, raw proposal, sanitized proposal/source pointer, edited projection, expected visual-review cue, and Prepare input. Use distinct synthetic names/roles so wrong guest/booker attribution is visible. A schema-valid visual answer is not an accuracy pass.
5. **Keep business authority separate.** After extraction, require visible staff edit/acceptance, selected native guest/agency/rate as applicable, fresh native Prepare and exact price. For actual write, one fresh grant, one Save, independent business-field readback. The R0 2028 synthetic result must not substitute for a priced Create.
6. **Make W14 acceptance source-scoped.** Fixtures should cover own-mail pre-stay/no ask, exact authored ask, quote-only ask, non-self mail, TBO/Travelit request vs notice, another provider, two independent current asks, first completion while second remains, hotel reply while PDF review remains, selected-file ack and matching native filing. Broad provider coverage needs a real labeled holdout/eval; do not infer it from two vendors.
7. **Report pipeline order truthfully.** Record merge SHA, check/review completion time, deployed process SHA, and proof SHA separately. Here #1020’s Greptile check completed after merge; #1026/#1028/#1031 automated checks also completed after their merge times. A green post-merge check is still evidence, but not a pre-merge release gate.
