## Pomerado generated-operation style vs current runners

Pinned `.439` package: the minter's own skill text tells it to drive the page's controls, catch the page's own data response (`Promise.all([page.waitForResponse(...), button.click()])`), and use in-page `fetch` only after the page reached the results (`dist/typescript/src/mint/skills.js:184-203`). The executor also exposes a CDP attach option (`execution/playwright-execute.d.ts`), but the standalone host rejects CDP (`standalone/session.js:7-10`), so a custom host would be needed to use Nava's slot. Generated operations therefore have the same mechanism as the current hand-written runners (Playwright + page responses + in-page fetch), not screenshot computer use or a supported API. Swapping would change authorship and repair speed, not the failure surface. Live HMS output was not observed.

Start disjoint booking UI, preparation, Add-On readiness, protective cancellation fixes and native date diagnosis where the active-workflow/file/slot rules allow. Only actual API/state dependencies and mutation conflicts create integration waits. Given subscription pressure, propose Luna preparing isolated scaffolding/tests and Grok spending its capacity on native semantics and real blockers rather than constant polling or blanket extra reviews. A bounded faster-model rescue is justified only by measured critical-path reduction, not model prestige.

Keep current-head remote gates, review, deploy and property canaries. Reject both full-run orchestration plumbing as T0 and pretending a small one-line behavior fix needs a whole new framework. Existing scripts wait and notify; no new LLM watchdog. Score dollars and elapsed time per accepted behavior with retries/review/proof included, not PR counts or raw model unit price. Deferred work remains in the accepted completeness target.
