## Findings and adjudication

| Finding | Decision and source-backed reason | Plan response |
|---|---|---|
| F1 P0: trusted same-page login is unspecified | **Accept as a design gap**, not proof that every possible secure bridge is impossible. The native worker protocol contains `execute` and `credential`, not a host login request; the worker owns the page and serializes requests. `execute` accepts source text. | Specify a dedicated trusted worker login request, IPC/executor changes and the existing semaphore. Do not send secret in authored script text, receipts or prompts. No claim of complete same-user isolation or reliable JavaScript string zeroing. |
| F2 P1: stop can cancel/lose artifact; one script can do multiple actions | **Accept.** `mcp-jobs.ts` interrupts the mint; the packaging finalizer can remove an unpublished directory. A post-result fence cannot undo extra actions inside a single dispatched script. | Fence subsequent live dispatches per mint, not the whole process. Inspect proposed actions before dispatch and keep offline finishing alive. Recheck actual feasibility rather than claim a prompt or source inspection is a sandbox. |
| F3 P1: explore alone never publishes | **Partly disagree.** `harness.ts` `publishableReceipt` excludes explore for its host-unavailable/close recovery predicate. But `mint-publication.ts` can retain a matching completed explore with the required result reference, and `standalone-sign-in.spec.ts` has a test asserting publication from explore after verified sign-in. Neither establishes that this hybrid mint publishes. | Explicitly distinguish those two mechanisms; require a real published artifact. Do not replace replay with a handwritten script or require unrequested exploration. |
| F4 P1: fresh run can land on the wrong page/root | **Accept.** `run-operation.ts` invokes `startPage` before generated operation code; fresh served calls use a new context. External host login does not itself create the native sign-in recipe. | Put trial login on the operation's own page after `startPage`, then verify HRCEN, then execute once. Runtime success remains unproved. |
| F5 P1: read-only and off-task behavior rely on prompts | **Accept the risk.** Vendor README says a controller may answer a request to switch to write and served runs do not recheck authority. A post-read fence alone cannot govern earlier dispatches. | Reject write effects/switches; inspect proposed live actions and fail closed if the screen-only scope cannot be established. Keep Guardian. This is not a proven general sandbox. |
| F6 P1: login helper may write the slot cache; empty worker environment is not isolation | **Accept.** The helper uses `HMS_SLOT_STORAGE_STATE` and `HMS_SLOT_PROFILE_DIR`; absent both it does not write the optional cache. Worker executes code in a Node worker with browser access. | Pass an environment without those cache variables; exclude sensitive captures while the password control is filled. Keep raw data under the approved private worktree. State the residual same-user/browser/network risk rather than add a new sandbox-proof gate. |
| F7 P1: lock wording could imply attaching the shared browser | **Clarify, not a confirmed browser-design contradiction.** The lock is a PostgreSQL advisory lock on a dedicated database connection, not a browser connection. Source does not establish a time-based lease or mandatory heartbeat. | Name the separate database holder and dedicated Pomerado context; monitor holder loss and stop work. Do not invent lease semantics or attach the shared slot by CDP. |
| F8 P2: rebuild can reset model overrides and screened errors can hide cause | **Accept.** Prior dist overrides were Terra/xhigh, not proof of Luna routing. Prior retrospective documents screened execution errors. Current runtime was not checked. | Check and apply Luna-max routing at execution and capture pre-redaction failures privately. Do not claim per-call model/effort without a receipt. |
| F9 P2: readiness and partial result are ambiguous | **Accept clarification; reject invalid readiness value.** This plan's contract uses `implementation-ready` or `requirements-only`; `revise-before-execution` is not a valid contract value. An implementation plan may contain explicit runtime uncertainty. | Resolve the known design gaps, say readiness is not runtime proof, and distinguish a completed experiment with blocked replay from the full proof passing. |
