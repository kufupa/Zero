### 3. Proposed target architecture [I]

1. One validated `Property` registry holds profile, installation, slot, create/rate/board/dinner policy, branding, reply copy, and eval identity.
2. Each mailbox transport maps to exactly one property; unknown or ambiguous mapping refuses, never defaults to HRCEN.
3. A property can own many transports; staff aliases are rows, not code branches.
4. `User` is global; `UserPropertyGrant(user, property, role)` is many-to-many.
5. Faith and Ayanda get HRDAV grants; each hotel team gets its own grants.
6. Keep mailbox ACL separate; effective access requires both property grant and mailbox access.
7. Resolve immutable `PropertyContext` once; pass through quote, party, prefetch, job, PDF, reply, and audit.
8. Installation credentials, browser slot, capabilities, lock, indexes, and caches are property-scoped.
9. A new hotel adds validated data/fixtures, not `if (property === 'HRDAV')`; no implicit CEN fallback.
