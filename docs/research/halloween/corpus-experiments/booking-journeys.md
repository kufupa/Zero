# Confirmation-anchored journey review

## Scope and method

Ten confirmation-PDF anchors were selected across the five stored dates. For each day, the selector favored one anchor with structural candidate links and a second without a prior same-thread booking word when available. This is a deliberately selected exploratory set, **not a random sample or evidence of production prevalence**. See [selector](select-booking-cases.py) and the [private candidate index](../../../../.private/corpus-experiments-20261030/booking-case-candidates.json).

We inspected saved parent emails, exact-confirmation mentions in other threads, selected same-recipient inbound candidates, and the later saved HMS Record View. The private packets below preserve source-row IDs, original corpus lines, timestamps, participant fields, message text, PDF candidates and HMS fields. The same-recipient pool can be large; the review helper initially shows all same-thread and exact-ID candidates, plus up to four same-recipient candidates. A missing match in a packet is not proof that no relevant message exists elsewhere.

- Source rows are saved messages, not proof of delivery; the all-mail export lacks a complete attachment inventory.
- Stored timestamp timezone semantics are unverified. HMS records were captured later and are not the state at the earlier decision point.
- A linked journey means evidence supports the relationship; it does not prove staff action was correct or establish every HMS event.
- Dates and prices below are only used where needed to explain the workflow. No guest names, addresses, confirmation identifiers, message IDs or raw text are published here.

## Practical implications

1. Search with several complementary signals. Exact confirmation references, message headers, matching guest/stay details and participants are useful together; same sender, domain or time alone can create false matches.
2. Preserve separate events for the inbound request, staff response, each PDF, later payment/voucher message and HMS observation. Do not flatten them into one thread or assume one email equals one booking.
3. Find and read the existing stay before proposing an amendment. Compare requested changes to evidenced current fields, flag uncertainty, and keep human approval for writes.
4. For quote-first evaluation, capture the original request independently from later booking outcomes. A confirmation-only set misses unanswered requests and quotes that never become bookings.

The other investigations in this folder separately cover request-first quote cases and the current code-level HMS capability inventory. Do not infer that any registered tool is active on the current deployment without separate runtime evidence.
