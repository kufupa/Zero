# Centurion 250 pilot: execution record

The approved [pilot plan](2026-11-01-centurion-250-pilot-plan.md) is the historical decision record. This file records execution-time changes and the frozen versions needed to repeat the work.

## Capability scenario

After the pilot plan was approved, the HMS work was re-phased into [Box 1](../../../plans/2026-11-01-002-hms-cloud-create-e2e-box-plan.md). Box 1 is a narrow CLI create tool and was documented as not started. Box 2 describes prospective wider create, amend, finance, document and quote work; native linked multi-room is explicitly out. The prior modular plan's native two-room pilot was withdrawn.

The pilot asks what could have helped **under the broader prospective Box 2 scenario**, assuming the named capabilities exist. This is not a claim about Box 1, a deployed workflow, guest writes or staff adoption. The model prompt and schema are part of the freeze below. In particular:

- Existing-stay/profile lookup, availability/pricing, approved create, supported stay amendment, finance context, generic approved document attachment where supported, and quote composition are prospective capabilities. Missing facts and ambiguous targets stay unknown; each write requires staff approval and Nava never sends.
- Box 2 proposes a loop of individual creates. That is not native linked multi-room or group/XLSX support. Only independently specified room requests with sufficient evidence can get conditional partial credit from that loop. Group requests involving more than 10 rooms in the same episode remain excluded; exactly 10 is not excluded by that threshold. Ambiguous totals are unknown.
- Generic attachment may help staff file a supplied POP or voucher, but OCR/intake and payment posting remain parked. Sender claim, historical file availability, accessible bytes and cleared payment are separate facts.
- Real-guest cancellation commit remains excluded. Lookup and preparation can be partial help; a TMC cancellation notification alone needs no action. An OTA/system origin is separate from work type; the documented integration-failure exception remains a policy conflict.

## Privacy and challenge design

The owner explicitly confirmed in this session that zero retention is enabled on the configured Azure resource. That confirmation is owner-reported; the resource setting was not independently inspected here. The runner requires the configured Azure Responses endpoint, uses `store: false` and no tools, and writes private outputs only. Guarded packets are rechecked against the pinned source and the privacy cleaner before sending. Model agreement is not ground truth.

The owner also authorized local checks and said the EC2 route may handle private email for this work. Selection, preparation and offline checks ran locally; model inference used Azure. No live mailbox query was needed.

Select all unembargoed development cases with a first-pass disagreement, plus up to 20 cases with complete agreement. Rank the agreement cases using `SHA-256(UTF-8(seed + NUL + 'agreement-check' + NUL + sourceRowId))`, with the pilot seed. Challenge calls use the same decision-time evidence and do not receive the sampling cues. Holdout and linked rows remain sealed until the development method is frozen.

For same-input variability, independently choose up to 20 of the 192 available development rows and 20 of the 50 holdout rows by ascending `SHA-256(UTF-8(seed + NUL + domain + NUL + sourceRowId))`, with domains `development-repeat` and `holdout-repeat` respectively and source-row ID as tie-break. Repeat each of the three model slots on the same prepared input; for the holdout repeat both the cleaned and guarded-original arms. Selection uses manifest identities only, not email content or labels, and was specified before holdout unsealing. These repeats describe model variability, not correctness.

Original-versus-cleaned arms share privacy guarding and HTML-to-visible-text conversion; the comparison can test subsequent decorative-separator and restricted repeated-boilerplate removal, not loss caused by their shared transformations. The saved snapshot lacks inbound attachment inventory and bytes. Linked metadata from the older export was observed later and cannot establish that a document was available at the historical decision point.

A pre-draw, aggregate-only metadata check found that all 11,211 saved inbound rows carry a single array-valued canonical `Message-ID`, matching the row's `messageId`. The selector and independent audit also support a single array-valued header when the row field is unavailable. An ID match is a candidate link, not proof of duplicate delivery.
