# Audit D — Ponytail (over-engineering / complexity only)

Scope: `apps/server-pilot/src/**` + `scripts/` + `deploy/`. Lens: complexity/YAGNI/stdlib/native only.
Correctness, security, performance are explicitly out of scope (see other audit tracks).
Context: single-hotel pilot, solo dev, 1 EC2 + 1 RDS, ~50 users, 1 shared mailbox, ~1k emails/day.

No code was modified. Report only.

## High confidence

1. `delete:` `apps/server-pilot/src/lib/driver/types.ts` — entire file is a placeholder shell (`IGetThreadResponse`, `ManagerConfig`, `MailManager`, `CenturionMailCategory`) explicitly commented `// TODO(task-4/6): mirror full shape from legacy driver types` / `// TODO(task-6): mirror full method surface`. Zero importers anywhere in the repo (`apps/mail` never imports `@zero/server/driver/types`; only self-references in `dist/`). It's a package.json `exports` entry ("./driver/types") kept "resolvable" for a future task that hasn't started. Replacement: nothing — delete the file and the export line; re-add when task 4/6 actually needs it. Gate: re-add only when a driver-manager abstraction is actually implemented. [apps/server-pilot/src/lib/driver/types.ts:1-33, apps/server-pilot/package.json exports]

2. `delete:` `requireMailboxAccess()` + `requireMailboxAccessFactory()` — two full functions (with ~45 lines of justifying comments) wrapping `resolveMailboxContext` + error mapping, re-exported from the package barrel. Zero call sites anywhere in `apps/server-pilot/src` or `tests/` outside their own definition/export. Every route uses `mailboxProcedure` middleware directly; nothing "holds a (userId, transportId) pair outside a tRPC procedure" as the comment speculates. Replacement: nothing; the middleware (`mailboxProcedure` in trpc.ts) is the single source of truth already. Gate: re-add `requireMailboxAccess` only when a concrete caller outside a tRPC procedure needs it. [apps/server-pilot/src/trpc/trpc.ts:151-208, apps/server-pilot/src/trpc/index.ts:15-16]

3. `delete:` `customProviders` auth-provider machinery — `customProviders: ProviderConfig[] = []` is always empty; `isCustom` and `customRedirectPath` fields on `ProviderConfig` are never set `true`/populated anywhere in the repo. `main.ts` maps over it every request to always produce `[]`, and `isProviderEnabled` carries an `if (provider.isCustom) return true` branch that can never execute. This is legacy-multi-provider scaffolding (mirrors `apps/server`'s OAuth-app custom-provider feature) with no product need in a single-provider (Google) pilot. Replacement: drop `customProviders`, `isCustom`, `customRedirectPath`, and the `customProviderStatus` block in `main.ts`; `/api/public/providers` returns `authProviderStatus` alone. Gate: re-add if/when a second, non-registry OAuth provider is added. [apps/server-pilot/src/lib/auth-providers.ts:14-18,49, apps/server-pilot/src/main.ts:4,40-47]

4. `delete:` dead re-export in `mail-helpers.ts` — `export { and, eq, desc, asc, isNotNull, isNull, sql, exists };` forwards drizzle-orm operators through this module, but every consumer (`mail.ts`, `drafts.ts`) imports these operators directly from `drizzle-orm`, not from `mail-helpers.js`. Zero importers of this re-export. Replacement: nothing, delete the line. [apps/server-pilot/src/trpc/routes/mail-helpers.ts:53]

5. `yagni:` `RealSmtpTransport` — a class that implements `SmtpTransport` but its `send()` body is `throw new Error('Real SMTP send not enabled in pilot pass...')`. It's only reachable when `SMTP_ENABLE_REAL === 'true'`, a flag nobody sets (not in pilot env docs, not in any script, not in tests except to prove it throws). Unlike `RealPop3Client` (a genuine, working implementation used in production when `POP3_HOST` is set), this "Real" class does no work — it's speculative scaffolding for a task explicitly marked out of scope. Replacement: delete `RealSmtpTransport` + the `SMTP_ENABLE_REAL`/`forceFake` branch in `createSmtpTransport`; keep `FakeSmtpTransport` as the only transport and the `SmtpTransport` interface for when real-relay work actually starts. Gate: re-add when a real SMTP/Exchange relay is actually wired (tracked in `deploy/deferred-real-mail-readiness.md`). [apps/server-pilot/src/mail/send/smtp.ts:66-105]

## Medium confidence

6. `yagni:` `schema-contract.test.ts` "cuts stale table shapes" / "drops connection-era and de-scoped tables" tests — asserts ~12 unrelated schema exports are `undefined` (`staffMember`, `mailSnooze`, `connection`, `oauthApplication`, `userHotkeys`, etc.). This is a negative-existence census: it doesn't test behavior, only that old names haven't been re-added — brittle ceremony that breaks/needs editing on any unrelated schema rename and provides no regression protection a TypeScript compile error on an actual re-add wouldn't already give (these are named exports consumed elsewhere; removing them again would be a deliberate act, not an accident this test would catch first). Replacement: delete the two negative-census `it()` blocks; keep the positive "exposes required context columns" test, which documents real behavior. [apps/server-pilot/tests/schema-contract.test.ts:15-20,49-58]

7. `yagni:` `deploy-config.test.ts` string-grep tests — 5 of 7 tests are `readFileSync(...) + expect(...).toContain(...)` against `nginx.conf`, `deploy-ec2.sh`, `write-ec2-env.sh`, and `main.ts`, asserting exact substrings (e.g. the full CSP header string, `'sudo nginx -t && sudo systemctl reload nginx'`). These test that specific text exists in a file, not that the deployed behavior works (nginx config isn't parsed/validated, the shell script isn't executed). Any reformat of the CSP header or renaming a service breaks the test for no behavioral reason. Replacement: for solo-dev pilot scale, either drop these to a single "file exists and non-empty" smoke check, or replace with an actual `nginx -t` / shellcheck run in CI if regression protection is wanted. [apps/server-pilot/tests/deploy-config.test.ts:14-50,85-94]

8. `shrink:` duplicated `spawn('aws', ...)` subprocess helper — `awsGetSecret()` in `scripts/load-50-users.ts` (lines 101-131) and `runAws()` in `scripts/seed-prod.ts` (lines 25-38) implement the same "spawn aws CLI, collect stdout/stderr, reject on nonzero exit" pattern independently. Replacement: one shared `runAwsCli(args): Promise<string>` helper (e.g. in a small `scripts/lib/aws-cli.ts`) used by both. ~25 lines saved. [apps/server-pilot/scripts/load-50-users.ts:101-131, apps/server-pilot/scripts/seed-prod.ts:25-38]

9. `shrink:` repeated JSON-credentials-map parsing — `loadPasswords()` in `load-50-users.ts` has 4 near-identical blocks (`PILOT_PASSWORDS_JSON` env, `PILOT_PASSWORDS_FILE` file, Secrets Manager) that each do `JSON.parse(...)` then loop `for (const [email, value] of Object.entries(parsed)) out[email] = typeof value === 'string' ? value : value.password;`. Replacement: extract `normalizeCredentialsMap(raw: string): Record<string,string>` once, call it from all three branches. ~15 lines saved. [apps/server-pilot/scripts/load-50-users.ts:133-186]

## Low confidence

10. `yagni:` `envVarInfo` / `EnvVarInfo` diagnostic metadata on `ProviderConfig`, surfaced through `/api/public/providers`'s `envVarStatus` array — this exists to tell the frontend login page *why* Google OAuth isn't configured (source, default value, which var is unset) for exactly one provider. Reasonable for one entry, but it's a generic diagnostics sub-schema for a registry of one. Not flagging for deletion (the FE's login page may render this), but note it as the kind of generality that should not grow further while the pilot has one provider. [apps/server-pilot/src/lib/auth-providers.ts:1-5, apps/server-pilot/src/main.ts:20-38]

11. `yagni:` `note_is_pinned_idx` / `user_settings_settings_idx` — a plain btree index on a low-cardinality boolean (`is_pinned`) and a btree index on an entire `jsonb` column with no operator class (can't support containment queries; only useful for full-value equality, which nothing in the codebase does — no `eq(userSettings.settings, ...)` query exists). Both are pre-existing schema carried from the legacy app rather than new server-pilot design, and at 50-user/1k-email/day scale indexes cost only write overhead, not correctness. Flagging as "index nobody reads" per the audit's own db-index hunt criterion, but this borders on the performance lens that's out of scope here — treat as informational, not a cut recommendation. [apps/server-pilot/src/db/schema/app.ts:33,52]

## Not over-engineered (approved)

- **`apps/server-pilot/src/trpc/wire-compat.ts`** — NOT a needless shim. It does real, non-trivial shape translation (recipient-object-vs-bare-string coercion, comma-separated address parsing for legacy draft composers, DB-row-to-FE-`ParsedMessage` mapping including RFC822 `references` header join/split). It's exercised by two dedicated wire-contract test files and consumed by both `mail.ts` and `drafts.ts`. Routes accepting the frontend's shape directly would just push this same transform logic (inline, duplicated) into every route handler. Correctly factored, not speculative.

- **`apps/server-pilot/src/mail/ingest/pop3-client.ts`** — hand-rolling the POP3 protocol (USER/PASS/UIDL/RETR/DELE/QUIT, dot-stuffing, line buffering over `net`/`tls`) is the lazy-correct call here, not the lazy-wrong one. POP3 has no actively-maintained modern Node client library worth the dependency-risk trade for ~400 lines of well-scoped protocol code; the `Real`+`Fake` split is a genuine working pair (unlike `RealSmtpTransport` above) — `RealPop3Client` is the actual production path when `POP3_HOST` is set, not a stub.

- **`apps/server-pilot/src/storage/s3.ts`** — `RealS3Storage`/`FakeS3Storage` behind one `S3Storage` interface is a legitimate Real+Fake pair: `RealS3Storage` is a full working implementation (not a throw-stub), the fake is used by ~10+ tests to assert stored bytes, and the ingest worker genuinely runs against either depending on env. Not yagni.

- **`apps/server-pilot/src/trpc/index.ts`** — a re-export barrel, but it's the actual npm-style package boundary (`package.json` `"./trpc": "./src/trpc/index.ts"`) that `apps/mail` imports (`@zero/server/trpc`) for the `AppRouter` type. Internal code (`main.ts`) imports `router.ts` directly and bypasses it, which is correct — the barrel exists for the one thing barrels are actually for: a stable external import surface.

- **`apps/server-pilot/src/mail/ingest/limits.ts`, `attachment-filename.ts`, `sanitize-email-html.ts`** — each is a small, single-purpose module doing one thing well. `sanitize-email-html.ts` correctly delegates to the `sanitize-html` npm package rather than hand-rolling an HTML sanitizer (hand-rolling that would be the actual over-engineering/security risk). Not bloated.

- **`apps/server-pilot/src/db/ssl-config.ts`** — 4-line function reading a bundled CA cert. Can't get much leaner; not a finding.

- **`apps/server-pilot/src/mail/ingest/parse-message.ts`** — uses the `mailparser` npm package (`MailParser`) for streaming MIME parsing rather than hand-rolling RFC822/MIME parsing. Correct call — MIME parsing is exactly the kind of thing you don't hand-roll.

## net

net: -120 lines, -0 deps possible (all cuts are internal dead code/tests; no dependency removals identified — every dependency found in use, e.g. `mailparser`, `sanitize-html`, `@aws-sdk/client-s3`, `@aws-sdk/client-secrets-manager` all have real, non-speculative call sites).

Breakdown: ~33 (driver/types.ts) + ~58 (requireMailboxAccess/Factory + index.ts export lines) + ~10 (customProviders block) + 1 (mail-helpers re-export) + ~18 (RealSmtpTransport + branch) ≈ 120 high-confidence lines; medium-confidence test/script cuts (~2, 3, 8, 9) would add another ~60-80 lines but are judgment calls on test value, not counted in the headline number.
