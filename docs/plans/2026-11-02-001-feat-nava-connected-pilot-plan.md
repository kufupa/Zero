# Nava connected pilot plan

Owner discussion draft. An independent Opus review challenged the full task-level estimate and functional-parity scope; its material findings are incorporated below and the revised draft returns for review. The batch-approval design is proposed, not implemented. This is not authorization to implement, deploy, change flags, send mail or access production.

## Goal Capsule

- **Outcome:** Staff open real incoming mail in Outlook or webmail. Nava identifies each request, preloads relevant HMS facts, shows a clear editable workspace, and helps staff complete the supported action with explicit approval and review.
- **Target:** Aim for the fastest complete pilot. The owner accepts a two-hour plan if a shorter target cuts too much; neither 90 nor 120 minutes is a hard cutoff or a proven ETA. Estimate the full requested scope independently and do not call incomplete slices finished.
- **Strategy:** Functional UI parity with current Cloud contracts, plus thin Cloud orchestration. Audit supported dropdowns, forms, inputs, validations, outputs and status states across both hosts. Keep the V1 look and avoid visual redesign for its own sake. Reuse infrastructure only where verified useful.
- **Later owner clarification, 2026-11-02:** “when I say a fresh UI, I don’t mean spending time on a UI design. I’m referring more to ensuring full UI parity in the dropdowns, forms, inputs, and outputs, because that is the most important thing. Make sure the contracts are up to date, valid, and current so everything works.” This clarifies the earlier fresh-UI direction. Exact message time was not retained in this planning context.
- **Authority:** Current owner direction plus `PRODUCT.md` and `AGENTS.md`; this plan is discussion only. Human approval for writes; Labtest-only live proof under current rules. Nava drafts but never sends. Do not accept penalty dialogs or retry uncertain writes blindly. Respect guest privacy, mailbox/property access and both pane surfaces.
- **Stop conditions:** Identity ambiguity, missing property authorization, unverified write effects or uncertain save. Report exact partial state. Never erase another session's work.

## Product Contract

### Requirements

- R1. Classify inbound mail into zero, one or multiple staff requests, with provenance and uncertain classifications visible. Apply general skip rules and the existing-stay self-mail rule; travel agents remain in scope. Do not equate a voucher or payment notice with an automatic financial action.
- R2. Preserve request identity by authorized mailbox, message, thread, property, request and, when applicable, stay. Persist useful structured extraction, staff edits, prelookup status/results, freshness and provenance without losing another worker's edits.
- R3. Run only relevant, property-scoped Cloud read lookups in the background. Distinguish loading, result, ambiguity, missing inputs, failure and stale data. Never fabricate room count, price, linked stays, identity or payment settlement.
- R4. Provide one coherent staff workspace in Outlook and webmail. Match current in-scope Cloud tool contracts for dropdowns, forms, inputs, outputs, validation and capability states. Support multiple requests/stays, requested versus known facts, corrections, next action, time-consuming states and human-readable failures. No duplicate facts or dead controls. Unsupported or unverified fields must be explicitly identified, not silently claimed or dropped.
- R5. Quote uses correct HMS rates and availability, room-type/count/occupancy rows, quote contact, permitted one-off/saved rates with required discount authorization, PDF, Excel and editable unsent reply. Handle no availability and optional alternatives per product rules.
- R6. Create permits explicit review/approval and guarded execution through reusable Cloud tools, with concrete success, screenshot and independent readback. Labtest proves exercised behavior only; current real-guest authorization remains separate.
- R7. Build reusable, appropriately authorized Cloud amendment and cancellation execution as well as review. Show current stay, requested change, status and exact confirmation where found; capture screenshots and independently read back saved effects. Preserve honest state when scope, cancellation policy or rate behavior is unknown. Real-guest execution remains fenced under current rules; cancellation is Labtest-only until the owner authorizes otherwise in the executing session. Never accept penalty dialogs.
- R8. Deliver a production-oriented multi-room wrapper, allowing multiple room/stay bookings per request where HMS supports them. Redesign or remove the overly broad Labtest same-name/arrival exclusion as needed for representative tests. Use request/room identity, appropriate write authorization and explicit reconciliation to prevent accidental duplicates. Do not claim separate bookings are natively linked/atomic without proof. Previously denied cross-thread association probes remain held.
- R9. Generate an editable reply and preserve it unsent. Prefer the existing host save/insert path where it works. Owner accepts copy/download as a speed-first pilot fallback when needed. Do not imply copied content or downloaded files were attached or sent. The phrase “sending a reply would be great” does not itself override “Nava never sends”; automatic sending requires an explicit policy/authority decision.
- R10. Autonomous verification, screenshots, exact final-head checks and production-equivalent evaluation distinguish proven results from staged-only and source-only capabilities.

### Acceptance examples

- AE1. A quote email asks for two room types: extract date ranges, room counts and occupants; show HMS prices per type, unknowns and editable quote; create no booking until staff approve.
- AE2. One email asks to change two confirmations: display both requests independently; prevent a late lookup for the first from overwriting the second.
- AE3. Cancellation preflight finds a confirmation: show status and dates; show room count as unknown unless complete scope is proven; no live real-guest cancellation.
- AE4. Occupancy Save raises HMS's actual 'Retain the current rates?' Yes/No/Cancel prompt: do not assume price semantics or re-dispatch. Surface the supported choice only once the save/prompt flow is proven safe; uncertain dispatch requires reconciliation.
- AE5. Staff switches messages during lookup: old result and screenshot cannot appear on the new message. Reopening the original restores the authorized persisted state.
- AE6. Voucher or payment mail for an existing booking is not a new booking and does not imply payment settlement; show identified evidence and the next supported staff action.
- AE7. A mailbox-to-itself pre-stay confirmation is existing-stay information, never a create request; verify both host selection and classification. Webmail currently filters direction and may exclude self-mail when marked outbound or when direction is absent; do not assume the case reaches classification.

### Product boundaries

Full intended scope is not a claim of 90-minute feasibility. New workflow slices can be delivered independently; incomplete slices must say what staff can and cannot do. Groups over ten rooms, XLSX processing, financial posting and automatic sends are not silently added to the run. The owner reopened multi-room for planning; that does not authorize previously denied association probes. For Centurion only, the owner considers a matching staff acknowledgement of supplied payment proof evidence of filing; retain the literal acknowledgement and inferred filing separately. Neither means payment settled (`docs/research/halloween/b2b-dashboard/README.md:5`).

### Proposed architecture

1. **Admission:** On a stored inbound message, apply policy and classify. Separate routing decision from multi-label staff requests; preserve source evidence and confidence, including attachment references.
2. **Structured request:** Typed versioned request envelope keyed by authorized transport/message/request/stay. Separate source facts, staff edits, lookup results and immutable action outcomes. Validate schema and server-side access on each read/write. Track revisions so stale worker/UI updates cannot replace newer edits.
3. **Read coordinator:** Select only relevant Cloud reads; inject property server-side, never from model output; queue and deduplicate by appropriate property, message, request and freshness. Record status, evidence time, and source. Resolve ambiguity rather than auto-binding guests.
4. **Workspace:** Contract-correct shared presentation mounted in both hosts. Same request/capability contract; host adapter supplies selection and the supported reply path. Prefer existing unsent draft/insert where functional; copy/download is an owner-accepted speed-first fallback. Preserve selection scoping, request IDs and stale-result protection. Staff sees incoming ask, verified current HMS facts, proposed edits, and one primary next action.
5. **Execution:** Staff reviews and explicitly approves supported writes. Tool boundary verifies authorization and identity, dispatches once, captures screenshot and returns confirmed/failed/uncertain. Independently read back where a write is claimed; unknown remains unknown. Keep each stay's outcome distinct.
6. **Reply:** Build editable reply/PDF from verified result and staff choices. Use the host’s actual unsent-draft path if available; otherwise offer copy/download with truthful labels. Never silently send.
