# Pomerado and parallel delivery shape

## Goal Capsule

Choose the next delivery strategy without shrinking booking completeness, overclaiming Phase 1 proofs, or replacing useful deterministic HMS tools without evidence. Prioritize an early useful Pomerado trial and efficient parallel work. This is shaping, not a product execution launch.

Original words: `docs/context/asks/2026-10-27-pomerado-parallel-shaping-owner-voice.md`. Prior accepted target: `docs/plans/2026-10-27-001-booking-completeness-plan.md`. Reassessment evidence: `docs/research/2026-10-27-next-run/pomerado-delivery-reassessment.md`.

## Product Contract

### Requirements

- R1. Preserve full new-booking parity: individual child ages, required/routine native fields, actual party binding, rate overrides/authorizers when used, approved notes, native status, and per-room saved outcomes.
- R2. Native Add-Ons remain a real native catalog/add/remove/readback workflow, not a quoted extra, note, or shuttle draft.
- R3. Trial Pomerado early as an operation-authoring aid. Useful first read covers native Add-On rows/catalog. Safe guarded Labtest add/remove and replay follow only passing browser/provider/lock/native readiness.
- R4. Do not assume existing deterministic runtime lacks browser automation or that Pomerado removes website-change risk. Distinguish model-driven authoring from deterministic replay and self-hosted core from cloud repair services.
- R5. Prepared-on-arrival means forwarded-message eligibility/extraction, property-bound durable party results, new-booking rates/availability, eventual overflow completion, editable pane hydration, and preservation of staff edits.
- R6. Reconcile newest Phase 1 evidence without treating its short list or this session's previous handoff as timeless truth. Multi-room pricing, backend pane-service create, rendered pane, native saved fields and email delivery are separate proofs.
- R7. Treat cancellation-before-fee-dialog as an applied cancellation with pending fee, not a safe no-op. Full-stay approval must bind current native facts. Paid/guaranteed and unknown-money policy remains held.
- R8. Discover supported native date-amend semantics, then compare bounded deterministic repair with proven Pomerado generation. Keep adult-amend pass separate from date support. No migration commitment before evidence.
- R9. Centurion cloud readiness is property-specific. Preserve current pause; do not infer quote/create/amend/cancel support from login/find. Keep native origin/tenant and visible Open HMS target correct per hotel.
- R10. Product writers use isolated area worktrees and narrow briefs. Maximize unrelated parallel work, serialize mutation integration and same-property HMS ownership, and honor actual API/state dependencies.
- R11. Route most explicit work to Luna max; conserve Cursor/Grok capacity for native semantics/high-risk work under current prescribed ownership. Any broader route change requires an owner decision. No blanket expensive reviewer swarm or constant LLM polling.
- R12. Compare total dollars and elapsed-to-accepted-result, including rework, review, deploy and native proof. Official API unit prices, gateway model identity, subscription capacity and observed model speed must not be conflated.
- R13. Keep current-SHA native/surface/price-truth gates. A CLI sidecar or dead inbox cannot certify staff workflow or mail delivery. Validate baseline failures on exact clean head, then fix useful harness defects.
- R14. Preserve named backlog and parked items. A window allocates effort; it does not redefine done. No new general orchestration framework as prerequisite to a small product slice.

### Acceptance examples

- AE1. Pomerado reads a real native Add-On catalog/row under the property lock with approved provider routing. Independent native evidence matches it. A public demo heading does not count as HMS fit.
- AE2. A Labtest Add-On Save loses its response. A fresh independent native read determines whether it applied before any retry. Existing booking is never recreated.
- AE3. An internal forwarded external booking schedules the appropriate reads while an own-mailbox pre-stay notification never offers new create. Forwarded From text remains evidence, not authenticated identity or party-binding authority.
- AE4. Staff select one company record. A late prepared result never replaces it, and fresh native create readback verifies the actual selected record rather than its display name alone.
- AE5. A collector receives no mail because ingest is inactive. The send proof is inconclusive, not failed or passed. HMS queue/dispatch and real receipt are scored separately.
- AE6. Cancellation reason confirmation applies cancellation before a fee modal. Nava reports applied/pending-fee and never calls it blocked. Unknown-fee eligibility stays conservative pending policy.
- AE7. A cheap worker finishes a slice but a shared gate or browser is occupied. Unrelated code continues; the expensive coordinator is not billed for repeated polling.
- AE8. A different property changes host/tenant. Only affected installation/control contracts and current-property canaries are updated. Unknown property never falls back to Centurion.

### Patch versus rewrite

Keep the deterministic workflow spine, queues, approval, receipts and staff pane. Use Pomerado to test whether native operation creation/repair becomes cheaper and faster. Property installation should become a shared source of truth where necessary rather than another host-string sweep. Exact native date/fee semantics must be established regardless of authoring tool.

Do not build a custom Pomerado CDP host, a browser fleet, a general workflow engine or new delivery framework for this first experiment. No general API/SLA claim from Pomerado's marketing applies to HMS until independently proved.

## Decision frontier

1. **Pomerado scope:** test native Add-On read/guarded write authoring, then consider other operations only from measured results; do not promise wholesale HMS migration. Recommendation: this bounded route.
2. **Routing trade:** minimize total dollar/elapsed outcome using Luna for most work and conserved Grok/native expertise; approve bounded faster-model rescue only for a measured critical-path blocker. Recommendation: balanced, not cheapest at any latency and not expensive models everywhere. Current risk ownership stays until decided.
3. **Cancellation policy:** may an operation cancel before a fee is known, and who controls resulting charge/waiver? Recommendation: staff-led until a safe pre-commit fee boundary is proved; never penalty Waive/OK.
4. **HRCEN pause:** keep paused or explicitly authorize a separate compatible quote repair in an executing session. Recommendation: decide separately from the HRDAV Add-On/booking experiment; do not infer unpause from discussion.

Dependent decisions on native Add-On charge/removal policy, provisional recipient/status, discount authorizers and actual property-used fields remain downstream. Native evidence should resolve facts first; only client policy comes to the owner.

No accepted execution plan is replaced here. This document may inform in-place enrichment of the existing booking-completeness plan after the frontier is settled. No implementation or orchestration launch.
