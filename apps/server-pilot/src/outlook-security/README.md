# Native device identity boundary (bridge v4)

Only the installed native process receives the random 32-byte device secret. It
generates a fresh UUID and secret per Windows user, protects the secret with
DPAPI CurrentUser and restrictive file ACL, and pairs using the operator's
10-minute one-use code. The operator binds *named staff user IDs* and *real
mailbox transport IDs* to the exact native-observed Outlook `StoreID`. Neither
the code nor the secret goes to the hosted web pane. A device persists until
explicitly revoked; the staff session has its independent 24-hour lifetime.

Enrollment requires `user.emailVerified=true` both in the operator CLI lookup
and transactional service validation. Better Auth currently configures
`requireEmailVerification:false`, so the operator must provision and verify
each named staff account before issuing its code; an unverified mailbox string
is not sufficient identity, and public signup remains disabled.

Set `NAVA_OUTLOOK_DEVICE_WRAPPING_KEY` to a separate, secret, canonical base64
encoding of 32 securely generated bytes in the server process. Do not use a
Better Auth secret or DB password. Missing/weak/wrong keys fail closed. Keep
this key stable across restarts; rotating it without re-enrolling devices
invalidates credentials. Do not log it or the plaintext device secret.

Operator-only shell workflow, with approved server DB credentials and the key:

```
pnpm --dir apps/server-pilot exec tsx scripts/outlook-device-operator.ts issue --store-id '<exact-native-StoreID>' --staff-email named.staff@example.test --transport-email shared@example.test
pnpm --dir apps/server-pilot exec tsx scripts/outlook-device-operator.ts revoke --device-id '<uuid>' --confirm-revoke
```

Repeat the `--staff-email ... --transport-email ...` pair to approve multiple
named users/mailbox transports for one store. Only the restricted operator
terminal displays the single-use code; the server persists only its SHA-256
hash. Enrollment is a public *redemption* endpoint, never public issuance.

## Contract for Task 3: staff tickets and signed native requests

`POST /api/outlook/native/challenge` takes `{deviceId}` and returns
`{nonce,expiresInSeconds:60}` with `Cache-Control: no-store`. The stateless
opaque nonce is a server-authenticated 60-second challenge even for unknown or
revoked IDs, so the response reveals no registration status and creates no
publicly requested DB rows. Native computes `X-Nava-Signature` as lowercase
hex HMAC-SHA256 with its 32-byte secret over the UTF-8 string formed by joining
these **seven** fields with `\n` (no trailing newline):

```
nava-outlook-v4
UPPERCASE_HTTP_METHOD
EXACT_URL_PATHNAME_WITHOUT_QUERY
lowercase_hex_sha256_of_exact_request_body_bytes
deviceId
unix_timestamp_seconds
nonce
```

Set `X-Nava-Device-Id`, `X-Nava-Nonce`, `X-Nava-Timestamp`, and
`X-Nava-Signature` headers. Task 3 should read raw request bytes *once* before
JSON parsing; reject query strings (or explicitly define their canonical
representation), then call `verifyDeviceRequest(db, {
deviceId,nonce,timestamp,signature,method,path,body }, wrappingKeyEnv)` with
the exact raw bytes and pathname. It returns `{deviceId,storeId,version}` or
`null`. Only valid signatures consume a nonce; a unique DB insertion makes
concurrent signed replays lose atomically. Verification records only the last
handshake timestamp and never grants mailbox access by itself. Call this
before any stateful registration or authorization native endpoint.

For staff ticket issuance and every signed native COM authorization, call
`isDeviceAuthorized(db, deviceId, staffSession.user.id,
mailboxTransport.id, nativeObservedStoreId)` and require `true`. That helper
joins operator-approved grants to current `mailbox_access`, an active
mailbox transport, the exact approved store, and a non-revoked device. Task 3
must also check the *live* Better Auth session, ticket scope/expiry, allowed
folder/operation and fresh native-observed store; the device ID is public and
not itself proof of possession. Per-navigation challenges, browser tickets and
read/mutation leases are separate Task 3/4 concerns: registration of a fresh
pane-navigation challenge must itself be a signed native request, expire within
60 seconds and be invalidated on revocation/navigation/logout. The web pane
gets only one-use browser tickets, never HMAC key material.

## Task 3 integration: native Task 5 / pane Task 6

Pane calls unauthenticated `POST /api/outlook/native/bootstrap` with `{}`;
response is solely `{protocol:"nava-outlook-v4",status:"ready",paneChallenge,
expiresInSeconds:60}` with `Cache-Control: no-store`. Send that challenge to
installed native; native requests `/challenge` and HMAC-signs
`POST /api/outlook/native/register-navigation` with `{paneChallenge}`.
Registration replaces the previous navigation, expires in 60 seconds, and
permanently refuses reusing any previously registered challenge for that
device, including an older challenge after a newer navigation. Before expiry (or when a ticket fails),
obtain a NEW bootstrap challenge and register it via native without reopening
the pane. The previous challenge and its tickets cease to authorize.
On logout or account switch, Task 5/6 MUST clear the native navigation epoch,
discard the pane challenge and all tickets, then register a new challenge
before any new ticket. Once a ticket was issued, the server additionally
rejects using that navigation from any different Better Auth session, even
when the same staff user signs back in immediately.

Pane calls `workstation.bridgeTicket` with `{deviceId,paneChallenge,action,
storeId?,operationId?,resources?,sourceFolderId?,destinationFolderId?}` and the
existing `x-zero-active-transport` header selecting the mailbox transport.
Actual legacy Better Auth cookie/session ID, verified named user, fresh
createdAt (<24 hours), mailbox access, store mapping and device authorization
are checked. Remote-admin sessions or injected test `sessionUser` cannot mint
tickets. Only the first signed-in ticket for a freshly registered navigation
may omit `storeId`: the server resolves the enrolled exact native StoreID after
all those checks and returns `{ticket,storeId,expiresInSeconds:60}`. The pane
must echo this exact `storeId` on every later ticket for that navigation;
an explicit mismatch is denied. Never derive the initial StoreID from a
pre-login native PING, browser-provided mailbox string, or a browser guess.
If the first ticket response is lost, obtain and register a fresh navigation
challenge before retrying without `storeId`. For moves the pane MUST declare exact resource EntryIDs and
source/destination folder EntryIDs. Supplied resource/folder declarations for
other actions are ticket-bound. Targeted item/attachment/template reads and
existing-item mutations MUST declare exact resource EntryIDs; folder listing
declares the source folder EntryID; folder creation declares its approved
parent source folder EntryID without inventing an as-yet-nonexistent message
resource. `GET_ACTIVE_EMAIL` and `CREATE_DRAFT` can begin without a known
existing message ID. Mutation operation IDs use the existing
`op_<unix-ms>_<32-hex-GUID>` format (<=15 minutes old, <=5 seconds future).

Native separately HMAC-signs exact raw body bytes for
`POST /api/outlook/native/authorize` containing `{ticket,action,storeId,
transportId,operationId?,resources?,sourceFolderId?,destinationFolderId?,
destinationKind?,nativeBatchConsent?}`. The native caller MUST independently
obtain store, resources, folder identities/kinds and actual consent from
Outlook COM; never trust the pane for these values. No response, non-200
response, elapsed scope, or changed operation authorizes COM. Native re-checks
store/navigation epoch on its STA thread before execution. Only native gets
the scope response (read <=60s, mutation <=15s, each capped at the earlier of
the Better Auth session row expiry and its original createdAt + 24 hours): exact action, mailbox/store,
resource IDs, folder IDs, approved folder IDs and `retry`. Never relay this
response to the hosted pane. Native SEND/DELETE are denied; independent
web-mail Send/Delete are unaffected.

A fully valid signed native `MOVE_EMAIL`/`MOVE_TO_SPAM` authorization returns
HTTP 409 `{ "code": "NATIVE_BATCH_CONSENT_REQUIRED" }` with
`Cache-Control: no-store` when 10+ explicit items or a rolling shared-mailbox
or per-device total above 25 moves/minute requires native consent. This does
not consume the browser ticket or insert a move receipt. Native must obtain
consent for that exact set of Outlook EntryIDs and destination, then retry
the same unexpired ticket and operation with `nativeBatchConsent:true` and a
fresh signed HMAC challenge/nonce; altered scopes or replayed signatures are
denied. Invalid, expired, revoked, consumed and mismatched tickets always
receive generic HTTP 403, never a consent hint. Any non-200 response remains
unauthorized to execute Outlook COM.

Operator provisions and revokes exact folder EntryIDs server-side (no PC
reinstall). This CLI requires restricted operator terminal, DB and wrapping
key, like device enrollment:

```
pnpm --dir apps/server-pilot exec tsx scripts/outlook-device-operator.ts approve-folder --store-id '<StoreID>' --transport-email shared@example.test --folder-id '<Folder EntryID>' --kind inbox
pnpm --dir apps/server-pilot exec tsx scripts/outlook-device-operator.ts approve-folder --store-id '<StoreID>' --transport-email shared@example.test --folder-id '<Folder EntryID>' --kind triage
pnpm --dir apps/server-pilot exec tsx scripts/outlook-device-operator.ts revoke-folder --store-id '<StoreID>' --transport-email shared@example.test --folder-id '<Folder EntryID>' --confirm-revoke
```

Native must identify Deleted Items/Outbox and descendants from actual Outlook
folder ancestry; the server additionally denies those reported destination
kinds and requires operator-approved source/destination IDs, with destination
kind `triage` or `inbox` (recovery) for `MOVE_EMAIL`, or `spam` for
`MOVE_TO_SPAM`. >=10 moves in one request or >25
moves per mailbox/device within a rolling minute requires exact native batch
consent before signing. Per-operation receipts persist across restarts;
identical retries do not increment counts, changed work with the same
operation ID is rejected. Native must still use its local operation cache to
avoid repeating already completed COM work on an approved retry.
