# Native device identity boundary (bridge v4)

Only the installed native process receives the random 32-byte device secret. It
generates a fresh UUID and secret per Windows user, protects the secret with
DPAPI CurrentUser and restrictive file ACL, and pairs using the operator's
10-minute one-use code. The operator binds *named staff user IDs* and *real
mailbox transport IDs* to the exact native-observed Outlook `StoreID`. Neither
the code nor the secret goes to the hosted web pane. A device persists until
explicitly revoked; the staff session has its independent 24-hour lifetime.

Set `NAVA_OUTLOOK_DEVICE_WRAPPING_KEY` to a separate, secret, canonical base64
encoding of 32 securely generated bytes in the server process. Do not use a
Better Auth secret or DB password. Missing/weak/wrong keys fail closed. Keep
this key stable across restarts; rotating it without re-enrolling devices
invalidates credentials. Do not log it or the plaintext device secret.

Operator-only shell workflow, with approved server DB credentials and the key:

```
pnpm --dir apps/server-pilot exec tsx scripts/outlook-device-operator.ts issue --store-id '<exact-native-StoreID>' --staff-email named.staff@example.test --transport-email shared@example.test
pnpm --dir apps/server-pilot exec tsx scripts/outlook-device-operator.ts revoke --device-id '<uuid>' --confirm-revoke
```

Repeat the `--staff-email ... --transport-email ...` pair to approve multiple
named users/mailbox transports for one store. Only the restricted operator
terminal displays the single-use code; the server persists only its SHA-256
hash. Enrollment is a public *redemption* endpoint, never public issuance.

## Contract for Task 3: staff tickets and signed native requests

`POST /api/outlook/native/challenge` takes `{deviceId}` and returns
`{nonce,expiresInSeconds:60}` with `Cache-Control: no-store`. The stateless
opaque nonce is a server-authenticated 60-second challenge even for unknown or
revoked IDs, so the response reveals no registration status and creates no
publicly requested DB rows. Native computes `X-Nava-Signature` as lowercase
hex HMAC-SHA256 with its 32-byte secret over the UTF-8 string formed by joining
these **seven** fields with `\n` (no trailing newline):

```
nava-outlook-v4
UPPERCASE_HTTP_METHOD
EXACT_URL_PATHNAME_WITHOUT_QUERY
lowercase_hex_sha256_of_exact_request_body_bytes
deviceId
unix_timestamp_seconds
nonce
```

Set `X-Nava-Device-Id`, `X-Nava-Nonce`, `X-Nava-Timestamp`, and
`X-Nava-Signature` headers. Task 3 should read raw request bytes *once* before
JSON parsing; reject query strings (or explicitly define their canonical
representation), then call `verifyDeviceRequest(db, {
deviceId,nonce,timestamp,signature,method,path,body }, wrappingKeyEnv)` with
the exact raw bytes and pathname. It returns `{deviceId,storeId,version}` or
`null`. Only valid signatures consume a nonce; a unique DB insertion makes
concurrent signed replays lose atomically. Verification records only the last
handshake timestamp and never grants mailbox access by itself. Call this
before any stateful registration or authorization native endpoint.

For staff ticket issuance and every signed native COM authorization, call
`isDeviceAuthorized(db, deviceId, staffSession.user.id,
mailboxTransport.id, nativeObservedStoreId)` and require `true`. That helper
joins operator-approved grants to current `mailbox_access`, an active
mailbox transport, the exact approved store, and a non-revoked device. Task 3
must also check the *live* Better Auth session, ticket scope/expiry, allowed
folder/operation and fresh native-observed store; the device ID is public and
not itself proof of possession. Per-navigation challenges, browser tickets and
read/mutation leases are separate Task 3/4 concerns: registration of a fresh
pane-navigation challenge must itself be a signed native request, expire within
60 seconds and be invalidated on revocation/navigation/logout. The web pane
gets only one-use browser tickets, never HMAC key material.
