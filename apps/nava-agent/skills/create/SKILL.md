# Create

Load `../references/common.md` and `../references/tools-and-proposal.md`. Then read `references/rules.md` and `references/replies.md`.

1. Use the current authored request: explicit book/reserve/proceed → Create; quote-only → Quote; an existing confirmation, status check or automated pre-stay notice → read the existing stay, not Create. Include quoted context only when the current message relies on it.
2. Split independent guests/stays. Bind each guest, dates, room quantity/type, occupancy/child ages, meal request, rate and contact to the correct stay. Reuse a value across rooms only when the request makes it shared. Inspect an attachment when a requested booking fact depends on it.
3. Publish a separate editable `propose` proposal for each supported guest/stay. Each proposal has exactly one booking and one `create` action, whose `booking_ids` contains that booking's `id` and whose `details` is `{}`. Put reservation fields in `booking.fields`, not action details. Prefill explicit facts. Keep unknown `adults`, `child_count`, `child_ages`, rate, source, track and guarantee editable and unknown. Use a room or rate code only when an HMS catalogue or quote returned it; otherwise leave it null and preserve the requested room or Standard Queen default as a staff-facing hint. Never put a room label in the native code field.
4. Preserve the exact field keys in [the tool contract](../references/tools-and-proposal.md): `first_name`, `last_name`, `arrival_date`, `departure_date`, `adults`, `child_count`, `child_ages`, `room_type`, `rate_plan`, `source_of_business`, `track`, `guarantee_type`, `guest_profile_id`, `guest_email`, `agency_name`, `agency_id`, `organization_name`, `organization_id`, `ar_account_name`, `ar_account_id`, `billing_reference`, `booker_name`, `booker_contact`, `reason_for_stay`, `note`, `guest_opt_in`, `cms_send`, `cms_message_id`, `cms_recipient`. Do not invent `meal_plan` or `organization_bill_to`; preserve unsupported meal/billing requests in the exact warning and do not claim a note fulfills them.
5. Keep the proposal compact: add field specs for requested/source-backed fields and essential guest, date, occupancy and room fields only. Leave optional unknown native choices to the Create editor, which adds those controls; do not generate field specs for every optional null. Use brief evidence with message IDs and null quotes, not full email text. This keeps multi-room proposals within the output limit.
6. Use native rate/availability results for rate code, meaning, price and availability. Company/employer is not rate eligibility or bill-to; agency/source, market, track, guest and payer are separate. Keep unsupported but editable choices in the proposal; use `needs_info` only when a material guest/stay fact cannot be inferred or selected, and `staff_review` only for an unresolved native limitation or conflict.
7. Set `native_result:null`. `cms_send` defaults on; set `cms_recipient` to the known requester and keep it editable. The Create editor supplies the HMS `cms_message_id` default; never put the email's message ID in that field. Staff reviews/edits, then triggers Prepare and Go. Agents never click Go for a real guest. Confirm only after readback verifies the saved guest/stay; after an uncertain Save, reread HMS before any retry.

Use the HRCEN native fill order in `references/rules.md`. The referenced corpus counts describe a curated request/reply set, not saved-field accuracy or a hotel-wide policy.
