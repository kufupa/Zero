# Create

Load `../references/common.md` and `../references/tools-and-proposal.md`. Then read `references/rules.md` and `references/replies.md`.

1. Use the current authored request: explicit book/reserve/proceed → Create; a request to assist with rooms for specified guests and dates framed as a reservation or booking is also Create; quote-only → Quote; an existing confirmation, status check or automated pre-stay notice → read the existing stay, not Create. Include quoted context only when the current message relies on it.
2. Split independent guests/stays. Bind each guest, dates, room quantity/type, occupancy/child ages, meal request, rate and contact to the correct stay. Preserve stated initials in `first_name` (for example, `B` or `L.E`); do not discard them for lack of a full name. If unsure which part of a guest's name is the surname, leave the name fields for staff and preserve the full source name in the note. Set `guest_email` when the request identifies the guest's email, or the sender is the guest; an agency's email is not the guest's email. Preserve a named company or organization, including one identified in the subject, acronym or signature, in its sourced role; keep a separately named agency, invoice recipient or payer in its own role. Reuse a value across rooms only when the request makes it shared. Inspect an attachment when a requested booking fact depends on it.
3. Publish one editable `propose` proposal per supported guest/stay. For a request for multiple rooms on that stay, put one booking entry per room in the same proposal (e.g. two rooms means two bookings with distinct IDs). Use one `create` action whose `booking_ids` lists all those IDs and whose `details` is `{}`. Keep occupancy per room; a per-person price is not a guest count. The pane derives the room count from the booking entries. Put reservation fields in `booking.fields`, not action details. Prefill explicit facts. Set `adults` and `child_count` for each room from the request; preserve stated occupancy. When the adult count is unstated, default to one adult per named guest assigned to that room who is not identified as a child, or one adult per room if none are assigned. When children are not mentioned, default `child_count` to zero. If children are mentioned without a count, leave `child_count` null and add an editable `field_specs` entry with provenance `unknown`. Record the source message ID and the words that mention children; include the attachment ID when applicable. Keep unknown `child_ages` and source editable and unknown. For HRCEN, use editable `BAR` rate plan only when no rate or board is stated or agreed; `NGI` guarantee and `BAR` track are editable defaults when unspecified. Mark default field specs `default`. Preserve an explicit rate, including a requested rate category or accepted quote, and its amount, limit and pricing basis for staff; do not set a numeric price override. For a requested rate or room, use the matching native code from HMS catalogue or quote results, not one inferred from the company or room wording. If the requested room is unresolved, keep its type as a hint and leave `room_type` null. If the requested rate is unresolved, keep the terms visible, leave `rate_plan` null, and offer valid catalogue candidates for staff to choose. If no room type was requested for an HRCEN room, use the verified Standard Queen code (`STQN`) as its editable `room_type` and label its field spec `default`. Preserve every explicitly requested room type. Never put a room label in the native code field. Infor requires a booking source for HRCEN. Preserve another explicitly supplied source if it matches the native catalogue; otherwise use native E-Mail (`EMA`) as the editable default for an email booking. Keep source, agency and organization separate. Resolve named parties as in step 4; an unresolved required party stays editable.
4. Search `hms_search_parties` for each company/organization and agency named in the request, subject or signature, including an acronym, independently of the selected rate. Set the appropriate `kind` (`organization` or `agency`) and `field: name`; search by the sourced name or domain and bind the returned editable ID and name when there is a single matching party in that role. Keep agency and organization distinct and leave ambiguous or unmatched IDs for staff. A company alone does not establish rate eligibility or the payer. For a stated rate or board phrase such as government, DBB or B&B, compare its meaning with returned native rate-plan descriptions and select the matching code as an editable choice. If multiple choices match, offer them for staff; if none match, leave `rate_plan` unresolved. For an unresolved requested rate, include an editable `rate_plan` field spec with `unknown` provenance and source-message evidence so the default does not overwrite it. Do not substitute BAR for a stated rate or board request, and do not infer a price.
5. Preserve the exact field keys in [the tool contract](../references/tools-and-proposal.md): `first_name`, `last_name`, `arrival_date`, `departure_date`, `adults`, `child_count`, `child_ages`, `room_type`, `rate_plan`, `source_of_business`, `track`, `guarantee_type`, `guest_profile_id`, `guest_email`, `agency_name`, `agency_id`, `organization_name`, `organization_id`, `ar_account_name`, `ar_account_id`, `billing_reference`, `booker_name`, `booker_contact`, `reason_for_stay`, `note`, `guest_opt_in`, `cms_send`, `cms_message_id`, `cms_recipient`. Do not invent `meal_plan` or `organization_bill_to`; preserve unsupported meal/billing requests in the exact warning and do not claim a note fulfills them.
6. Keep the proposal compact: add field specs for requested/source-backed fields, the default rate plan, and essential guest, date, occupancy and room fields only. Leave optional unknown native choices to the Create editor, which adds those controls; do not generate field specs for every optional null. Use brief evidence with message IDs and null quotes, not full email text. This keeps multi-room proposals within the output limit.
7. When a native guest-profile read returns the profile matching the email guest, set its returned native ID in that guest's `booking.fields.guest_profile_id`, editable for staff. Use native rate/availability results for rate meaning, price and availability. Company/employer is not rate eligibility or bill-to; agency/source, market, track, guest and payer are separate. Keep unsupported but editable choices in the proposal; use `needs_info` only when a material guest/stay fact cannot be inferred or selected, and `staff_review` only for an unresolved native limitation or conflict.
8. Set `native_result:null`. `cms_send` defaults on; set `cms_recipient` to the known requester and keep it editable. The Create editor supplies the HMS `cms_message_id` default; never put the email's message ID in that field. Staff reviews/edits, then triggers Prepare and Go. Agents never click Go for a real guest. Confirm only after readback verifies the saved guest/stay; after an uncertain Save, reread HMS before any retry.
9. On the resumed turn after Create Go is done with the readback confirmation and stay ID, if the original selected message supplied a voucher or proof-of-payment PDF for that stay, read Filing and publish a separate Filing proposal for that exact selected message and PDF, tied to the readback confirmation and stay. Staff reviews it and triggers Filing Prepare and Go. Do not create a pending target, infer a confirmation or stay, or file during the initial Create turn.

Use the HRCEN native fill order in `references/rules.md`. The referenced corpus counts describe a curated request/reply set, not saved-field accuracy or a hotel-wide policy.
