# Create

Load `../references/common.md` and `../references/tools-and-proposal.md`. Then read `references/rules.md` and `references/replies.md`.

1. Use the current authored request: explicit book/reserve/proceed → Create; a request to assist with rooms for specified guests and dates framed as a reservation or booking is also Create; quote-only → Quote; an existing confirmation, status check or automated pre-stay notice → read the existing stay, not Create. Include quoted context only when the current message relies on it.
2. Split independent guests/stays. When the mail lists N guest names with N rooms (or one room each under GUEST NAMES / officials), publish N create bookings in list order — bookings/0 is the first listed guest. Bind each guest, dates, room quantity/type, occupancy/child ages, meal request, rate and contact to the correct stay. Preserve stated initials in `first_name` (for example, `B` or `L.E`); do not discard them for lack of a full name. Title + two tokens on an officials/GUEST NAMES list is usually `Surname Firstname` (Mr Swartbooi Bernadus → last=`Swartbooi`, first=`Bernadus`); Western `Title Firstname Lastname` stays Firstname/Lastname. If still unsure which part is the surname, leave the name fields for staff and preserve the full source name in the note. Set `guest_email` when the request identifies the guest's email, or the sender is the guest; an agency's email is not the guest's email. Preserve a named company or organization, including one identified in the subject, acronym or signature, in its sourced role; keep a separately named agency, invoice recipient or payer in its own role. Reuse a value across rooms only when the request makes it shared. Inspect an attachment when a requested booking fact depends on it.
3. Publish one editable `propose` proposal per supported guest/stay. For a request for multiple rooms on that stay, put one booking entry per room in the same proposal (e.g. two rooms means two bookings with distinct IDs). Use one `create` action whose `booking_ids` lists all those IDs and whose `details` is `{}`. Keep occupancy per room; a per-person price is not a guest count. The pane derives the room count from the booking entries. Put reservation fields in `booking.fields`, not action details. Prefill explicit facts. Set `adults` and `child_count` for each room from the request; preserve stated occupancy. When the adult count is unstated, default to one adult per named guest assigned to that room who is not identified as a child, or one adult per room if none are assigned. When children are not mentioned, default `child_count` to zero. If children are mentioned without a count, leave `child_count` null and add an editable `field_specs` entry with provenance `unknown`. Record the source message ID and the words that mention children; include the attachment ID when applicable. Keep unknown `child_ages` and source editable and unknown. For HRCEN silent defaults from 56 live pre-arrival fills: guarantee `DEPREQ` (Deposit Requested) — never `NGI`. When an agency is bound, use `GTDAGT` (Guaranteed By Agent) and prefer the agency A/R. Government org: rate `NGOVDB`, track `GOV`, board DBB; only then add note line `Dinner Gov inclusive of R210.00 + 2 s/drink` (never for non-government DBB). Corporate: `NCOR1B`/`NCOR2B` + track `COR`. Prefer org/agency `hms_search_parties` defaults from stays before as_of. Use editable `BAR` rate only when no rate/board and no org default apply. Mark default field specs `default`. Preserve an explicit rate, including a requested rate category or accepted quote, and its amount, limit and pricing basis for staff; do not set a numeric price override. For a requested rate or room, map email room words through the native catalogue meanings to codes (HRCEN: twin→`STWN`, queen→`STQN`, king→`SKNG`, deluxe twin→`DLXTWN`, deluxe queen→`DLXQN`, deluxe king→`DLXKNG`, executive king→`EXKNG`, luxury king→`LUXKNG`, suite→`SUITE`, double/double room→`STWN`). "Single occupancy" / "for one person" sets adults only — never room_type `STQN`. Call `hms_read_catalogue` for `room_type` when resolving. "Standard" alone is not a bed type — do not treat it as `STQN`. If the email is silent on bed/grade, or says only "standard room"/"room(s)"/"single occupancy" without twin/queen/king/deluxe, bind org/agency then **must** use `defaults.room_type` from the `hms_search_parties` hit (agency default over org when both exist); only when that default is absent use editable `STQN` and label its field spec `default`. Never leave `room_type` null on a create propose — always publish a catalogue code (mapped, party default, or `STQN`) as editable. If a specific grade (deluxe/executive/luxury) is named without a bed, keep that grade in the hint and still set the closest catalogue code editable for staff. If the requested rate is unresolved, keep the terms visible, leave `rate_plan` null, and offer valid catalogue candidates for staff to choose. Preserve every explicitly requested room type. Never put a room label in the native code field. When parties return `defaults` (rate_plan, guarantee_type, track, source_of_business), prefer those as editable defaults when the email is silent on that field. Infor requires a booking source for HRCEN. Preserve another explicitly supplied source if it matches the native catalogue; otherwise use native E-Mail (`EMA`) as the editable default for an email booking. Keep source, agency and organization separate. Resolve named parties as in step 4; an unresolved required party stays editable.
4. Search `hms_search_parties` for each company/organization and agency named in the request, subject, signature or From travel-agency brand (Travel / Travel Consultant / `*.travel` / `*travel*.co.za` / brand token in From display or email local-part/domain), including an acronym, independently of the selected rate — do this **before** `proposal_publish` even when an organization was already bound. Set the appropriate `kind` (`organization` or `agency`) and `field: name`; search by the **exact sourced entity literal** (and its distinctive brand token / acronym when the full string is multi-word). When `selection` returns a single party, set `agency_id` / `organization_id` from that candidate’s `nativeId` and keep `agency_name` / `organization_name` as the **sourced email literal** (entity-literal), not a longer HMS trading-as expansion, unless the email itself used that longer form. Keep agency and organization distinct — a `Company:` guest employer does not replace a travel-agency From/signature bind — and leave ambiguous or unmatched IDs for staff, but never skip the agency search when From/signature looks like a travel brand. A company alone does not establish rate eligibility or the payer. For a stated rate or board phrase such as government, DBB or B&B, compare its meaning with returned native rate-plan descriptions and select the matching code as an editable choice. If multiple choices match, offer them for staff; if none match, leave `rate_plan` unresolved. For an unresolved requested rate, include an editable `rate_plan` field spec with `unknown` provenance and source-message evidence so the default does not overwrite it. Do not substitute BAR for a stated rate or board request, and do not infer a price.
5. Preserve the exact field keys in [the tool contract](../references/tools-and-proposal.md): `first_name`, `last_name`, `arrival_date`, `departure_date`, `adults`, `child_count`, `child_ages`, `room_type`, `rate_plan`, `source_of_business`, `track`, `guarantee_type`, `guest_profile_id`, `guest_email`, `agency_name`, `agency_id`, `organization_name`, `organization_id`, `ar_account_name`, `ar_account_id`, `billing_reference`, `booker_name`, `booker_contact`, `reason_for_stay`, `note`, `guest_opt_in`, `cms_send`, `cms_message_id`, `cms_recipient`. Do not invent `meal_plan` or `organization_bill_to`; preserve unsupported meal/billing requests in the exact warning and do not claim a note fulfills them.
6. Keep the proposal compact: add field specs for requested/source-backed fields, the default rate plan, and essential guest, date, occupancy and room fields only. Leave optional unknown native choices to the Create editor, which adds those controls; do not generate field specs for every optional null. Use brief evidence with message IDs and null quotes, not full email text. This keeps multi-room proposals within the output limit.
7. When a native guest-profile read returns the profile matching the email guest, set its returned native ID in that guest's `booking.fields.guest_profile_id`, editable for staff. Use native rate/availability results for rate meaning, price and availability. Company/employer is not rate eligibility or bill-to; agency/source, market, track, guest and payer are separate. Keep unsupported but editable choices in the proposal; use `needs_info` only when a material guest/stay fact cannot be inferred or selected, and `staff_review` only for an unresolved native limitation or conflict.
8. Set `native_result:null`. `cms_send` defaults on; set `cms_recipient` to the known requester and keep it editable. The Create editor supplies the HMS `cms_message_id` default; never put the email's message ID in that field. Staff reviews/edits, then triggers Prepare and Go. Agents never click Go for a real guest. Confirm only after readback verifies the saved guest/stay; after an uncertain Save, reread HMS before any retry.
9. On the resumed turn after Create Go is done with the readback confirmation and stay ID, if the original selected message supplied a voucher or proof-of-payment PDF for that stay, read Filing and publish a separate Filing proposal for that exact selected message and PDF, tied to the readback confirmation and stay. Staff reviews it and triggers Filing Prepare and Go. Do not create a pending target, infer a confirmation or stay, or file during the initial Create turn.

Use the HRCEN native fill order in `references/rules.md`. The referenced corpus counts describe a curated request/reply set, not saved-field accuracy or a hotel-wide policy.
