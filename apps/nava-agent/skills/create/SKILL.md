# Create

Read [common rules](../references/common.md), [proposal bindings](../references/tools-and-proposal.md), [field rules](references/rules.md) and [reply drafts](references/replies.md).

1. “Kindly reserve”, “book” or “confirm the rooms” after a quote is Create: carry forward the accepted terms and keep side questions secondary. An agency order asking staff to make a stay is Create even if formatted as a voucher. **Voucher Create vs Filing:** follow the shared decision in [triage routing details](../triage/references/rules.md). Staff forwards from Legacy (`@legacyhotels.co.za` / Martha / Kamala / `hotels@`) route on the **inner client request**; resolve agency from the inner client sender. Extract each requested guest, room and stay from the current order. Inspect supplied evidence when the request relies on it. Keep a shared value on every room it covers and an override only on its own room.
2. Publish **one grouped Create action** for a supported multi-room order: one `bookings[]` entry per requested room, in source order, with its assigned guest, dates and occupancy. Preserve every named guest and each explicit room, including separate guest/stay associations; flag unclear assignments instead of inventing them. List all booking IDs in the one `create` action with `details: {}`. The pane derives the room count from those entries. Larger orders outside the pane's booking limit go to staff review; keep their scope intact.
3. Put booking facts in `booking.fields`. Require both `first_name` and `last_name` under `/bookings/i/fields/{first_name,last_name}` for each room, with numeric index `i` in actual pointers. A combined `guest_name` alone does not satisfy Create. Respect evidenced surname-first order and keep initials as supplied. Prefill dates and occupancy, `room_type` and `rate_plan` as HMS catalogue codes (never invent a room code when bed/category is unstated), `board`, and `organization_name`/`agency_name` from `hms_search_parties` — when `sender_history` or a `[Client Memory Card]` supplies a learned agency/org for the sender domain, **use it** to resolve ambiguous candidates; always search `hms_search_parties(kind: "agency", ...)` with the sender (or inner forwarded client) domain for travel-agency senders. Put digit-bearing PO / order / voucher numbers (e.g. `1374219`, `PO 450012`, `Ggfs901`) in `billing_reference`; never a company/agency name. Emit `guarantee_type` only when the email states it (e.g. Agency To Pay / `GTDAGT`, Non-Guaranteed Individual / `NGI`, deposit / `GTDDEP` / `DEPREQ`, credit card / `GTDCC`) or `[Client Memory Card]` / party memory supplies it — never invent a guarantee. Leave `source_of_business` unset; code owns the HRCEN email `EMA` default (staff may edit). Add editable specs for essential and source-backed fields; leave unused optional controls to the editor. Keep an identifiable booking `propose` when catalogue, party or profile lookup is unavailable and the unresolved native choices can be filled by staff. Anchor yearless dates to the selected email receipt or the relevant requested stay in the thread. A clear booking commitment stays `propose` despite missing names, checkout, room split or child ages: leave them empty, list them in `missing`. Side asks (invoice, transfer, payment link) go in `warnings`, never `staff_review`.
4. Staff confirms and prepares the booking. After verified Create readback, if the original selected message also supplied a genuine voucher or POP for that new stay, publish a separate Filing draft using that exact file and the readback target. Do not publish a pending filing target.
