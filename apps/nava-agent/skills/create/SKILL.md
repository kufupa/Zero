# Create

Load `../references/common.md` and `../references/tools-and-proposal.md`. Then read `references/rules.md` and `references/replies.md`.

1. Use the current authored request: explicit book/reserve/proceed → Create; a request to assist with rooms for specified guests and dates framed as a reservation or booking is also Create; quote-only → Quote; an existing confirmation, status check or automated pre-stay notice → read the existing stay, not Create. Include quoted context only when the current message relies on it.
2. Split independent guests/stays. Bind each guest, dates, room quantity/type, occupancy/child ages, meal request, rate and contact to the correct stay. If unsure which part of a guest's name is the surname, leave the name fields for staff and preserve the full source name in the note. Preserve an explicitly identified guest company in `organization_name` for that booking; keep a separately named agency, invoice recipient or payer in its own role. An agency, billing instruction or sender signature alone does not establish the guest's organization. Reuse a value across rooms only when the request makes it shared. Inspect an attachment when a requested booking fact depends on it.
3. Publish one editable `propose` proposal per supported guest/stay. For a request for multiple rooms on that stay, put one booking entry per room in the same proposal (e.g. two rooms means two bookings with distinct IDs). Use one `create` action whose `booking_ids` lists all those IDs and whose `details` is `{}`. Keep occupancy per room; a per-person price is not a guest count. The pane derives the room count from the booking entries. Put reservation fields in `booking.fields`, not action details. Prefill explicit facts. Set `adults` and `child_count` for each room from the request; preserve stated occupancy. When the adult count is unstated, default to one adult per named guest assigned to that room who is not identified as a child, or one adult per room if none are assigned. When children are not mentioned, default `child_count` to zero. If children are mentioned without a count, leave `child_count` null and add an editable `field_specs` entry with provenance `unknown`. Record the source message ID and the words that mention children; include the attachment ID when applicable. Keep unknown `child_ages` and source editable and unknown. For HRCEN, use editable `BAR` rate plan only when no rate is stated or agreed; `NGI` guarantee and `BAR` track are editable defaults when unspecified. Mark default field specs `default`. Preserve an explicit rate, including a requested rate category or accepted quote, and its amount, limit and pricing basis for staff; do not set a numeric price override. For a requested rate or room, use the matching native code from HMS catalogue or quote results, not one inferred from the company or room wording. If the requested room is unresolved, keep its type as a hint and leave `room_type` null. If the requested rate is unresolved, keep the terms visible, leave `rate_plan` null, and offer valid catalogue candidates for staff to choose. If no room type was requested for an HRCEN room, use the verified Standard Queen code (`STQN`) as its editable `room_type` and label its field spec `default`. Preserve every explicitly requested room type. Never put a room label in the native code field. Infor requires a booking source for HRCEN. Preserve another explicitly supplied source if it matches the native catalogue; otherwise use native E-Mail (`EMA`) as the editable default for an email booking. Keep source, agency and organization separate. Search `hms_search_parties` for a source-backed sender company or agency even when the selected rate does not require a party. Set `kind` to `agency` or `organization`, `field: name`, and use the company or agency name (or its domain when only the domain is available). Set that party’s editable native ID and name only on a single match; leave unmatched optional parties empty. An unresolved required party stays editable; agency is not automatically the guest’s organization.
4. Preserve the exact field keys in [the tool contract](../references/tools-and-proposal.md): `first_name`, `last_name`, `arrival_date`, `departure_date`, `adults`, `child_count`, `child_ages`, `room_type`, `rate_plan`, `source_of_business`, `track`, `guarantee_type`, `guest_profile_id`, `guest_email`, `agency_name`, `agency_id`, `organization_name`, `organization_id`, `ar_account_name`, `ar_account_id`, `billing_reference`, `booker_name`, `booker_contact`, `reason_for_stay`, `note`, `guest_opt_in`, `cms_send`, `cms_message_id`, `cms_recipient`. Do not invent `meal_plan` or `organization_bill_to`; preserve unsupported meal/billing requests in the exact warning and do not claim a note fulfills them.
5. Keep the proposal compact: add field specs for requested/source-backed fields, the default rate plan, and essential guest, date, occupancy and room fields only. Leave optional unknown native choices to the Create editor, which adds those controls; do not generate field specs for every optional null. Use brief evidence with message IDs and null quotes, not full email text. This keeps multi-room proposals within the output limit.
6. When a native guest-profile read returns the profile matching the email guest, set its returned native ID in that guest's `booking.fields.guest_profile_id`, editable for staff. Use native rate/availability results for rate meaning, price and availability. Company/employer is not rate eligibility or bill-to; agency/source, market, track, guest and payer are separate. Keep unsupported but editable choices in the proposal; use `needs_info` only when a material guest/stay fact cannot be inferred or selected, and `staff_review` only for an unresolved native limitation or conflict.
7. Set `native_result:null`. `cms_send` defaults on; set `cms_recipient` to the known requester and keep it editable. The Create editor supplies the HMS `cms_message_id` default; never put the email's message ID in that field. Staff reviews/edits, then triggers Prepare and Go. Agents never click Go for a real guest. Confirm only after readback verifies the saved guest/stay; after an uncertain Save, reread HMS before any retry.
8. On the resumed turn after Create Go is done with the readback confirmation and stay ID, if the original selected message supplied a voucher or proof-of-payment PDF for that stay, read Filing and publish a separate Filing proposal for that exact selected message and PDF, tied to the readback confirmation and stay. Staff reviews it and triggers Filing Prepare and Go. Do not create a pending target, infer a confirmation or stay, or file during the initial Create turn.

Use the HRCEN native fill order in `references/rules.md`. The referenced corpus counts describe a curated request/reply set, not saved-field accuracy or a hotel-wide policy.
