# Create fields

- **Stay and name:** Put ISO `arrival_date` and `departure_date` on each applicable booking. For a yearless range, **anchor the year from dated quoted thread messages or the requested stay itself**, not from an unrelated receipt year when those conflict (Labtest / future stays often sit in the quoted thread). Fall back to the selected message receipt and plausible stay chronology, including year rollover. Preserve the established arrival if the checkout is ambiguous; set only the unknown date to null. Preserve source spelling and every explicit initial in `first_name`. Use labeled given/surname fields or clear list format to map name parts; do not reverse unlabeled names based on a title alone. Preserve ambiguous full name text for staff. Bind `guest_profile_id` only from a matching native profile. Use `guest_email` for the guest, not the agency; keep booker name/contact separate.
- **Occupancy and room:** Preserve per-room adults, children and ages. When adults are unstated, use a labeled default of the assigned adults if known, otherwise one per room. No children mentioned means editable zero; children mentioned without a count or ages stay unresolved. Headcount or per-person price does not establish room quantity. Put the HMS room code in `room_type` for an HRCEN catalogue code, exact category+bed (e.g. standard twin → `STWN`), or a class with one catalogue choice (executive → `EXKNG`, luxury → `LUXKNG`, suite → `SUITE`). For a silent room or bare standard/single without bed preference, leave null or use the labeled editable `STQN` default for staff verification; never invent Deluxe, Executive, Luxury, King or Twin. An explicit single room with a category maps to that catalogue bed family; single occupancy alone sets adults.
- **Meals and rate:** Record explicit **room-scoped** board in editable `booking.fields.board`: canonicalize `B&B` / bed and breakfast → `BB`; dinner bed and breakfast / "DBB" as a single plan → `DBB`; room only → `RO`. **"Bed and breakfast" (or B&B) plus a priced or optional dinner is still `BB`** — dinner is an add-on/extra, not DBB. Only the combined meal-plan phrase "dinner bed and breakfast" / explicit DBB sets `DBB`. Explicit `B&B` must set board `BB` (never leave null). Preserve any other or conflicting plan as source text. Never lift dinner/board from a footer or another room. This is draft intent, not a native inclusion claim. Put the HMS rate code in `rate_plan`, matching rate term and board from `hms_read_catalogue` (government DBB `NGOVDB`, government BB `NGOVB`, complimentary BB `CMPBB`; distinguish GDS/comp); keep the requested words/amount in staff note when no code fits. Match the native rate and meal choice where supported; do not replace an explicit rate or board request with BAR or invent an override. When silent, use verified party+board defaults or `[Client Memory Card]` / party memory; public BAR is an editable default only absent a conflicting preference.
- **Parties and billing:** Organization is the guest's employer or paying company. Agency is the booking intermediary (Travel With Flair, FCM, Tourvest, CWT). An agency's invoice addressee does not make it the organization — never install an intermediary as employer. **When the email names a company or department, always call `hms_search_parties(kind: "organization")` with that name and bind on a clear match.** Search agency too when evidenced, including the booker's agency in the signature, body, voucher or From display name even when a separate employer is present. Always pass that sourced name or acronym as `query` to `hms_search_parties`, plus the correct kind and sender host if known. Treat a dedicated agency mailbox localpart such as `sita3@nexustravel.co.za` as possible organization/account evidence: search that acronym or expanded name as the organization while still searching the agency separately. For a travel-agency sender, always also search `hms_search_parties(kind: "agency", ...)` with the sender domain (or inner forwarded client domain on Legacy staff forwards). When `sender_history` or a `[Client Memory Card]` provides a learned agency/organization for that domain, **use it** to pick among ambiguous candidates instead of leaving `agency_name` / `organization_name` blank — but never overwrite a mail-evidenced agency name when ID is still blank. The domain map is a shortcut; a domain miss is never the end of the search. If an earlier domain-only lookup missed, search the name before leaving any party field blank. Check candidates against the email, especially after a partial search. Copy the returned native name verbatim when it identifies the evidenced party (even if spelling or legal suffix differs); leave null when no returned name fits. Use the tool's selected ID only; several IDs for the same returned name can support the name alone. Employer does not establish rate or credit eligibility. Put numeric/alphanumeric PO, order or agency voucher numbers that contain **at least one digit** (e.g. `1374219`, `PO 450012`, `Ggfs901`, Travelit `1356971`) in `billing_reference` (max 50 characters). Prefer the order/PO token alone when the mail also cites a voucher (`Order 36484`, not `Voucher …; Order 36484`). Never put a company or agency name in `billing_reference`. Put addresses, VAT numbers and payment directions in the billing note.
- **Native choices:** Keep source, track, guarantee, agency, organization and A/R account separate. Prefer supported party defaults for silent choices and the verified agency A/R when applicable. Emit `guarantee_type` as a native code when stated in the email (map "Agency To Pay Supplier" / "Agency To Pay" / "Bill-Back" → `GTDAGT`, "Non-Guaranteed Individual" / `NGI`, deposit → `GTDDEP` / `DEPREQ`, credit card → `GTDCC`) or supplied by `[Client Memory Card]` / party memory. Never invent a guarantee. Do not spend inference on `source_of_business` — leave it null/omitted; code sets native `EMA` with default provenance on HRCEN email publish (staff may override). Do not assume a named party grants a rate or credit.
- **CMS:** Default `cms_send` on, off for Labtest. Prefill editable `cms_recipient` with the known requester; use the editor's HMS `cms_message_id` default, never the email message ID.
