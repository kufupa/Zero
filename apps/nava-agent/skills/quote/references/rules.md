# Quote criteria and prices

- **Dates:** Use explicit dates first. Resolve a yearless date range from the selected message's received date and the stated stay chronology, using the next plausible stay for a future request and carrying year rollover through the range. If still ambiguous, ask. Checkout is departure; preserve each requested segment rather than expanding it or adding a night. For an explicitly one-day event, keep the same date at both ends of the group without inventing a stay.
- **Room lines:** Keep each distinct quantity, accommodation preference, occupancy and scenario on its own `groups[].rooms[]` row. When the email states room category/bed, put the matching native HMS `room_type` code in editable `room_type` (deluxe/king/twin/luxury/executive/suite → catalogue codes such as `DLXKNG`, `STWN`, `LUXKNG`, `EXKNG`, `SUITE`); keep descriptive wording only when no catalogue code fits. Use the exact stated room quantity, including counts tied to room labels in prose or a table. If a stated guest count expressly requires single occupancy for each, set room `quantity` to that count. Otherwise use editable `quantity: 1` as a labeled default for a room quote with no stated count. Do not infer quantities from headcount alone, room-nights, old replies or native options.
- **Occupancy:** Keep stated adults, children and ages per room. “Accommodation for one official,” or accommodation for one named adult with no other travellers mentioned, means one adult in one room. Read forwards and RFQ attachments too. If one room is requested for a party, that party count is per-room. When the stated number of adult travellers equals the number of requested occupied rooms, use one adult per room. Otherwise require stated allocations or explicit single occupancy for multiple rooms. Default to `children: 0` and `child_ages: []` when no children are mentioned; ask for unclear counts or ages. A room category alone does not establish occupancy.
- **Board:** Put the requested preference in each applicable group or room. Use `BB` for the public BAR default, `DBB` for B&B with dinner as a hotel add-on, `BLD` for full board and `RO` for room only. Carry dinner as a separate extra with its requested scope and a null price unless the hotel has supplied one. Board text does not establish inclusion or a native rate code.
- **Parties and extras:** Keep the requester or booking entity in `party_name`, separate from guest or beneficiary. Search relevant agency or organization for negotiated rates; verified native eligibility is separate from a name or domain match. Keep public rates separate from negotiated options. Put each requested extra in editable `details.extras[]` as `{description, quantity, price}`, including its stated unit and nulls for unknown amounts. An included meal is not an extra.
- **Property:** If mail explicitly names a different hotel or the hotel is ambiguous, keep the property field unresolved and put the relevant mail evidence on that field. When the mail is silent, staff Prepare uses the selected mailbox property.
- **Native inputs:** Use property, stay dates, quantity and occupancy per room, with stable IDs. Keep event-only groups out of HMS. Search named agencies/companies via `hms_search_parties` and publish the matching `agency_name` or `organization_name`. Omit sales strategy and rate codes for the default. When the guest asks for any available room, omit room codes, beds and features rather than listing the catalogue. Otherwise prefer exact catalogue `room_type` codes for stated category/bed constraints; bed-only preferences (single, twin, double, queen, king) may stay as wording when no full room code is implied. Breakfast is board, not a room feature. Use nightly summary. Keep staff overrides distinct from HMS prices.
- **Native outputs:** Keep room/rate meaning, dated price, currency, basis, inventory and restrictions distinct. Show an official total only when HMS supplies it. If summing nightly prices, label the sum nonofficial.
