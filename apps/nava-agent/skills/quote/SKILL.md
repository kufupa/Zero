# Quote

Use the shared rules and tools-and-proposal bindings already supplied in the pinned context; do not load them again. If either is absent, load that file with `skill_read({"skill_name":"quote","path":"../references/common.md"})` or `skill_read({"skill_name":"quote","path":"../references/tools-and-proposal.md"})`. The `../` is required for both shared files; retry the exact call if a needed shared file is unavailable. Only `references/rules.md` and `references/replies.md` are relative to Quote without `../`.

When the current message explicitly asks to make or proceed with a new booking and also asks for the price, load Create and publish its booking proposal. Preserve the price question for staff or as a separate Quote when appropriate.

1. Gather property, dates, rooms/quantity, per-room adults/children/ages, room/meal requests, native party context. Keep distinct room groups inside one client quote unless separate quotes requested or staff split. For partial, rate-match or conflicting requests, publish an editable `quote-1` group with confirmed facts; use `needs_info` and ask specific questions. Leave unknown or conflicting dates and adults null; preserve conflicts in `missing` and do not infer allocations. Per Q02, when no children are indicated, use editable `children:0` and `child_ages:[]` as a labelled default, not a fact; if children are indicated but their number or ages are unclear, clarify. When room quantity is unstated (no explicit `N rooms` / `N ×` / `N - RoomType` line), use editable `quantity:1` as a labelled default, not a fact — never leave it null and never derive it from guests, adults, kids, delegates or attendees; if several explicit room lines are listed, give each its own rooms[] entry with that line's quantity.
2. Call `hms_read_catalogue` only when the request supplies native codes needing validation or explicitly asks a code question. Resolve those codes and meanings only from the verified thread property and native catalogue. Leave unknown property and native codes null or absent in the draft; never invent a code or price or copy an example into the request. Request other kinds only for an explicit party or code question. Apply board defaults in R5 only on a native-supported plan; company/government wording guides search, not eligibility. Staff typed code/price overrides stay distinct from native prices.
3. Once required criteria are complete and any supplied native codes are verified, call `hms_quote` with stable quote ID and separate date/room groups. Start with nightly `summary` and the native option limit; lowering the limit can hide matching options and make the search partial. Read native availability, price and restrictions per group. Absent combination/criteria unavailable ≠ sold out. No quote read holds rooms.
4. Publish grouped criteria in `actions[].details` with editable `field_specs` even when incomplete; preserve known dates and room bindings, and expose unknown required fields as null for staff. Every quote action must include at least one `groups[]` entry with a `rooms[]` row — never publish `groups: null` or omit `rooms` on a quote draft. Set each room `quantity` from an explicit current-inbound room line only; if unstated use editable `quantity:1`; never copy a room count from a quoted staff reply or from pax/delegates/adults. Give every action a stable, nonempty `quote_id`, including an incomplete draft. Omit unknown optional code arrays. Set editable `party_name` to the requesting or booking company or agency, not the traveller or the beneficiary on whose behalf an agency books. Preserve any separately named beneficiary and agency in their own context. Search HMS parties by the source's company/agency name or sender domain when available, using the appropriate `kind` and `field: name`; use a single matching party's name for its role, and leave ambiguous or unmatched identities for staff rather than inventing a legal name. Keep a named guest separately in editable `guest_name` context. When separate quotes are requested, publish one action per person or party with its own unique `quote_id` and requested scope. A party may have multiple room groups within its action.

   Put the requested meal/board preference in editable `details.board`, with a field spec at `/actions/N/details/board`; if groups have different board requests, use editable `/actions/N/details/groups/M/board` instead. Map current-inbound wording: dinner / DBB / D,B&B / dinner bed and breakfast → `DBB`; bed and breakfast / B&B / BB only → `BB`; breakfast+lunch+dinner / full board → `BLD`; room only / RO → `RO`. Preserve requested alternatives such as `BB or RO` as alternatives. If no board is stated, record `BB` as a labelled editable default, not a source fact — never leave `details.board` null on a quote draft. This is a preference for staff, not a claim that meals, a rate or a price are available or included; select a native plan only when supported. Keep verified native `mealPlanBases` separately and pass only supported inputs to `hms_quote`.

   For each requested extra, such as a shuttle, transfer, lunch, dinner or early check-in, add a separate item under that action's `details.extras` as `{description, quantity, price}`, with source-backed description and quantity where stated and null for an unknown price. Add editable field specs at the actual `/actions/N/details/extras/M/description`, `/quantity` and `/price` paths, so staff can price each item. Preserve the requested unit or basis in the description. Do not call a requested extra "not a quote item" or invent its price; an included meal is not an additional charge unless requested separately. These items are proposal metadata, not native `hms_quote` inputs. Staff edits and rechecks the room request only after required criteria and any supplied native codes are validated. Use `native_result:null`; backend owns the capture and native display rows. Do not claim a client-facing artifact includes extras until it actually does. Official room totals are native-supported; staff-entered extra prices remain separately identified.
5. Draft one cover email for all requested parties, plus one signable PDF and editable Excel per party (R4 owner 2026-11-17; 44/338 attachment-template, 23/338 inline prices). Staff selects verified native options after recheck. Say attached only once all files are on the unsent draft. Greet known first name; never name the company in the reply.
6. Native confirmed unavailability → 1–3 sentences; say which requested nights/rooms remain available and offer to quote. Sister hotel only if staff adds (R2: 6/12 alternatives, 1/12 sister hotel). End turn; no `hms_prepare` or `hms_save`. Later explicit proceed → create skill.

Tools: `skill_read`, `mail_read_thread`, `mail_read_attachment`, `hms_read_catalogue`, `hms_search_parties`, `hms_quote`, `proposal_publish`, `reply_draft`. Exact [inputs/proposal](../references/tools-and-proposal.md); unavailable capabilities explicit.

Example: a partial quote draft when no children are indicated. Replace each null with a source-confirmed value when known; never send this incomplete draft to `hms_quote`.

```js
const details = {quote_id:"quote-1",property_code:null,details:"summary",board:"BB",
  groups:[{group_id:"stay-1",arrival_date:null,departure_date:null,rooms:[
    {id:"room-1",quantity:1,adults:null,children:0,child_ages:[]}
  ]}]};
const field_specs = [
  ["/actions/0/details/property_code", "Property", "text"],
  ["/actions/0/details/groups/0/arrival_date", "Arrival", "date"],
  ["/actions/0/details/groups/0/departure_date", "Departure", "date"],
  ["/actions/0/details/groups/0/rooms/0/quantity", "Rooms (editable default)", "number", "default"],
  ["/actions/0/details/groups/0/rooms/0/adults", "Adults", "number"],
  ["/actions/0/details/groups/0/rooms/0/children", "Children (editable default)", "number", "default"],
  ["/actions/0/details/groups/0/rooms/0/child_ages", "Child ages", "text"],
].map(([path,label,control,provenance="unknown"]) => ({path,label,control,provenance,
  editable:true,required:true,error:null,options:[],evidence:[]}));
proposal_publish({workflow:"quote",disposition:"needs_info",reason:"Quote criteria need confirmation",
  bookings:[],actions:[{id:"quote-1",type:"quote",booking_ids:[],details}],
  field_specs,missing:["Confirm missing quote criteria"],warnings:[],reply_draft:null,native_result:null});
```

One `rooms[]` entry per different occupancy/board. `required` and `preferred` may carry `roomCodes`, `rateCodes`, `bedTypes`, `mealPlanBases`; these arrays are nested under `required` or `preferred`, not directly on the room. Publish editable fields for dates, room quantity, per-room occupancy, and supplied constraints at their actual paths. A field-spec path must resolve to a value in the proposal: omit specs for optional code arrays and parent objects that are absent. Include the actual `adults`, `children` and `child_ages` paths together, even when the age array is empty, so staff can correct the classification in one edit. Keep reported ages in evidence when classification is provisional. Never invent a room count from a guest count. Missing required facts → `needs_info` with the actual gaps; do not make a speculative HMS read.
