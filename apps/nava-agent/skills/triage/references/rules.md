# Routing details

- Use `triage/skip` for completed hotel or staff replies, sent invoices or confirmations, routine OTA/channel notices, template acknowledgements, spam, job applications and thanks with no pending instruction. A pre-stay notice with a confirmation concerns an existing stay. Preserve any new instruction carried by the selected message.
- A notice about settling an existing stay by virtual card is `triage/skip` if informational, `triage/staff_review` if staff must follow up. Neither creates a filing action. An incidental virtual-card reference does not change the route of a separate lodging order or actual voucher or POP submission.
- Commission, invoice-copy, payment-link and already-incurred cancellation-fee inquiries on their own are `triage/staff_review` when staff help is requested, with no actions. Completed replies and informational notices about them still skip.
- For an actual existing-stay status or reconfirmation request, use a scoped reservation read/search, not a guest-profile read. If staff needs a lookup draft, use action `type: "triage"` and editable `details.lookup`: `{reservation_id, guest_name, arrival_date, departure_date}`, with the known confirmation and surname, and null for unknowns. Put field specs under the action's actual lookup path. Keep separate stays distinct and report failed reads as unresolved.
