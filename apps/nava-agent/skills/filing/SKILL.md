# Filing

Read [common rules](../references/common.md), [document rules and native order](references/rules.md), and [reply drafts](references/replies.md).

1. Use `mail_read_thread`. Look at the selected inbound first. Propose Filing when the current message is a submission (voucher / POP / “see attached” / “please file”) **and** `mail_read_thread` lists ≥1 PDF on that selected message. Always emit at least one filing action (`voucher_submission`, `payment_proof_submission`, or `attach_document`) with `details.attachment_id` set to that PDF’s exact `id` from the thread payload — even when the filename looks like a confirmation letter, the extracted text is thin, or the stay confirmation is still unknown (leave `confirmation_number` null for staff). Prefer `payment_proof_submission` when the sender says payment/POP/proof; otherwise `voucher_submission` for voucher/attach wording; `attach_document` only when the ask is generic. Never publish `needs_info` with `actions: []` solely because the PDF looks like a confirmation letter or because confirmation is unresolved. An earlier quoted voucher, promised payment, invoice request, or pro-forma alone (no selected PDF) is not a Filing task.
2. **Bind `confirmation_number` before publish.** Pull candidates in this order and set `booking.fields.confirmation_number` to the unique native stay (with `-N` suffix) when one matches:
   1. Attachment `confirmation_hints` and `extracted_text` (`confirmationNumber` JSON key, or plain `NNNNNNNN-N`).
   2. Filename `HRCEN_Confirmation_Letter_<conf>.pdf`.
   3. Selected subject/body and earlier thread (patterns `n°`, `Confirmation Letter`, `confirmation`, `RES:` / reservation numbers that HMS resolves).
   4. When still absent: `hms_search_reservations` by guest surname + arrival/departure from the voucher/POP text or body; use the unique hit.
   Prefer the exact native confirmation returned by HMS. If HMS has not verified the stay, keep a uniquely labeled, fully suffixed hotel confirmation from the selected message or selected PDF only as an editable `booking.fields.confirmation_number` on a `staff_review` draft. Warn that it is unverified; leave `reservation_id`, `current_state`, and `native_result` null. If the evidence conflicts or no supported number is available, leave the confirmation null for staff. Treat supplier, invoice and bank references as lookup candidates only; never invent a stay suffix. For a compact or padded suffix, use the native suffix HMS returns. Resolve each voucher or PDF to its own stay; never apply one file’s confirmation to another. Cite HMS evidence if only HMS shows the suffix.
3. Treat filename and sender wording as source hints. Unless document text is truly available, say the PDF contents were not read and staff must check the selected file and its booking before Prepare. Do not claim paid, filed or duplicate. Do not call absent attachment or filing tools.
4. For each selected PDF and intended stay, preserve a separate booking and action, leaving the target unknown when unresolved; use `native_result: null`. Set `booking.property_code` to HRCEN and `booking.fields.confirmation_number` to the exact native confirmation (including stay suffix), or null if unavailable. Include an editable field spec for each booking's `/fields/confirmation_number`; when unavailable, list the missing reference for staff. Put only sourced guest names or ISO stay dates in the corresponding fields. Use the following action:
   - `type`: `voucher_submission`, `payment_proof_submission`, or `attach_document`, appropriate to the current request.
   - `booking_ids`: the one booking ID.
   - `details`: `{message_id, attachment_id, description}`. Use the selected inbound message ID and an exact PDF ID listed on it. Use a short editable label such as “Accommodation voucher” or “Proof of payment”, at most 200 characters. Keep the longer explanation in the proposal summary and leave bank or card data out of the description.
   - Add editable field specs for each action's `/details/description` (text) and `/details/attachment_id` (select, source PDF IDs and filenames from this message only). The source message ID is fixed. Cite the source message/attachment in evidence. Use only the field-spec keys in the shared bindings; put explanations in `error` or `warnings`, not extra keys such as `path_note` or `required_note`.
5. Staff checks the actual PDF, confirms the exact booking and runs Prepare on the edited revision. The worker checks the HMS Documents list and opens the unsaved form with the selected PDF and description. It reports the observed document code and list coverage. Nothing is uploaded or sent.

Tools: `skill_read`, `mail_read_thread`, scoped `hms_search_reservations`/`hms_read_reservation`, `proposal_publish`. Use the complete proposal shape in [bindings](../references/tools-and-proposal.md); staff Prepare replaces any model Prepare or Save for this workflow.
