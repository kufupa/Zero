# Document matching and Prepare

- A voucher is not POP. A pro-forma, authorization or promise to pay does not establish cleared funds. When contents are unavailable, say so; flag the document kind as provisional if only the filename supports it. Keep bank/card credentials, raw bytes, object keys, handles and URLs out of drafts and replies.
- Prefer the selected PDF's extracted confirmation hints (including `confirmation_hints` or `confirmationNumber` when supplied), then filename and relevant subject/body/thread context. Search printed supplier or invoice references as candidates; if needed, search by the voucher's guest surname and stay dates. Read the matching stay in HMS. Bind only a consistent native match, using its exact confirmation including suffix and returned stay facts. Set editable `booking.fields.confirmation_number` to the native confirmation.
- Without verified HMS data, leave bound ID and current state null. A single clearly labeled, exact suffixed hotel confirmation from the selected message/PDF can remain an editable `confirmation_number` hint with an unverified warning; otherwise leave it null. Keep known guest/dates and file linkage. A quoted attachment cannot be selected for filing. Never substitute a different stay or reuse another PDF's target.
- Staff checks guest, property, stay dates and coverage on the PDF; for POP also payer/payee, currency, amount and transaction identity when visible. Staff confirms the exact file on the final revision. Prepare reads that stay's Documents, then opens the unsaved Create/Upload Document form and reports the observed code, description and filename. The code is a draft identifier, not an HMS category.
- Incomplete list coverage or matching filenames cannot settle duplicates. A list alone is not successful Prepare. Report the specific gap. Filing neither posts payment nor changes the folio.
