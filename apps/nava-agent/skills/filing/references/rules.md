# Filing rules + native order

- F01 Split voucher submission, POP submission, payment question, invoice request. More than one may apply. Invoice/status/refund/payment-link question alone never files a document; answer only from supported current read/artifact, otherwise staff review.
- F02 Inspect actual supplied file. Voucher/confirmation: issuer/payer where shown, property, booking/ref, guest, dates, covered rooms/charges. POP: payer, payee, amount/currency, transaction reference/date and intended stay where shown. Record evidenced fields only; contradictions or weak stay link → review. Do not expose card credentials or raw bank details in proposal/reply.
- F03 Match exact property + native reservation + guest/stay + document scope. Number from older confirmation, same sender/thread, hotel domain or time proximity supplies candidate only. Use parent/reply header chain where available; follow later corrections/cancellations. A PDF issued before cancellation does not prove active stay. Preserve separate room/guest scope and file identity; do not clone across linked stays unless explicitly covered and each supported target verified.
- F04 Filename/label ≠ content. Unpaid pro-forma, card instructions, promised payment ≠ POP. Missing file → ask for it after inspecting source. Agency/GDS/no-reply ≠ OTA-only notification; keep supplied agency voucher. AirPlus category/billing handling unverified; inspect actual supplied document and review unsupported mapping.
- F05 Receipt, attachment, posted payment, cleared funds distinct. No payment/refund/folio mutation. Partial folio/balance never proves settled. Do not assert paid or send bank details/refund policy absent supported authority.
- F06 Existing document identity requires same stay, file content or reliable exact file identity, intended category. Filename alone cannot settle duplicate or uncertain upload. Verified duplicate → no write, factual draft if useful; incomplete document list → unknown, not absence.
- F07 Native staging order: verified Stay 360 → Documents → Create/Upload Document → current document code + meaning → description → selected file. One explicit file per operation. Agent passes source handle/identity via supported adapter; worker fetches bytes, maps native fields. No invented document codes or raw bytes in proposal. Backend catalogue has no document-kind enum; adapter must expose choices or hand off.
- F08 Real guest Save after Go, Labtest per common. Fresh exact-stay readback must establish intended stored document; verify metadata and stored bytes/content identity separately when available. Upload HTTP 200/refresh or loaded filename alone ≠ durable/exact readback. `not_dispatched` = upload not released; `awaiting_readback` = attempted upload + matching refresh, not save proof; `uncertain` = may have applied. Re-read fresh first; incomplete list/ambiguous identity → staff review, never blind retry.
- F09 Missing file/target/category → specific clarification; unsupported document/payment action → staff review. Do not decline valid agency document just because no adapter; do not claim filed when only staged. Distinct attached files/stays reconciled independently.

## Staff fields

Property/reservation → guest + dates + room scope → source attachment (name/type/size + stable message/file IDs) → actual role + payer/amount/ref if relevant → native document code/meaning → description → file selection → upload on Go → fresh document readback. First steps are staff-facing matching order; native control order code → description → file is script evidence.

Use supported file size/property limits. A partial document list (`refreshVerified:false`, `complete:null`) cannot resolve uncertain filing. Folio balance alone does not prove payment.
