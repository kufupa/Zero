# Amend field rules

- Supported patch keys: `arrival_date`, `departure_date`, `adults`, `child_count`, `room_type`, `rate_plan`, `first_name`, `last_name`, `booker_name`, `booker_contact`, `reservation_note`. Keep unsupported deltas visible for staff rather than inventing fields or propagating a change to other stays or a guest profile.
- Date targets are ISO dates. Preserve every explicitly requested target even when already matched in HMS; flag the no-change result. **Anchor the year from dated quoted thread messages or the requested stay**, not from an unrelated receipt year when those conflict. A request for an earlier arrival changes arrival; a stated checkout is the departure, not an occupied night. Do not derive the patch from a mismatch between an earlier document and current HMS. Always publish the requested arrival/departure (and name) patch on `booking.fields` even when `reservation_id` is still null — staff bind the stay later. Carry explicit board wording such as "with breakfast" / B&B into a supported note or warning when board is not an amend patch key — do not silently drop it.
- For an explicit room change put a `room_type` code from `hms_read_catalogue`: single/double/queen → STQN, twin → STWN, king → SKNG, deluxe/executive/suite → that family. Never ask the guest to clarify standard room wording; staff can edit. Rate/board prose is not a `rate_plan` code. An invoice correction alone is not a room rate change.
- Prepare reads the saved stay and requires verified first name, last name and arrival in `current_state`. If only documentary identity is available, staff selects the stay first. Changes to dates, occupancy, room or rate need native re-rating; a separate quote does not establish amendment availability.
